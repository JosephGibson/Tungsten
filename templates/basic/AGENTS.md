# AGENTS.md

Rules for this game's repository; `CLAUDE.md` imports this file.

## Layout

- `tungsten.json`, `input.json` and `assets/` sit in the game's folder, its working directory: run `cargo run` and `cargo test` from there.
- `src/main.rs` builds the app. `src/game.rs` is the game's plugin: its systems by stage, the setup its first frame needs, and its text. `src/states.rs` holds the states, `src/components.rs` the components and `tests/` the tests.
- When the game passes about three components or two features, move each feature into `src/features/<name>/`: `mod.rs` holds its `Plugin`, `components.rs` and `systems.rs` the rest. `game.rs` only adds the feature plugins. A component two features share goes in `src/shared.rs`. A feature plugin registers its own prefab components, data kinds and systems, as a kit item does. The kit's scene names and data kinds are reserved: the registries fail startup on a duplicate.

## Rules

- Use the engine's public API, `tungsten::…`, and nothing else from its sources.
- Name assets by their ID in `assets/manifest.json`, never by file path (the engine's `D-009`).
- An entity kind the game places more than once, or that a level file places, is a prefab: a file under `assets/prefabs/` listed in the manifest's `prefabs`, with its sprite, tag and components. Register each component a prefab names, deriving `Deserialize`, in the plugin's `build`. Spawn one with `world.prepare_prefab(id, position)` and `.spawn(world)`, or from a system queue it with `CommandBuffer::spawn_prefab`; a state passes its `SceneEntity` through `.with(..)`, and a prefab queued from an entity with `CommandBuffer::spawn_prefab_from(entity, prepared)` takes that entity's `SceneEntity`, as the kit's `Spawner` spawns. A Tiled object whose class names a prefab spawns through `world.spawn_map_objects(map, origin)`.
- A definition several prefabs share (an effect, an item, a table) is a data entry: register its kind with `world.register_data_kind::<T>("<kind>")` in the plugin's `build`, list its file under the manifest's `data.<kind>`, and name it from a component's field as a `tungsten::core::DataRef<T>`, by ID or written in place; every ID a prefab or an entry names is checked at load, whatever the order.
- Read actions through `ActionMap`, never keys; bindings live in `input.json`.
- Draw through `Sprite` entities and tilemaps, which the engine draws by default. Add the game's own sprite batches, quads and text in its plugin's `build`, through `world.resource_mut::<Extracts>()` and `add_sprites`, `add_quads` or `add_text`: they draw after the defaults, in the order added. Replace a default (`replace_sprites`) only on purpose: the engine's `Sprite` entities and tilemaps stop drawing.
- Take generic gameplay from `tungsten::kit` before writing it: `game::register` adds `KitPlugins::set()` before the game's plugin, and a prefab composes the kit's components by their scene names, as `prefabs/player.json` does (`tags`, `action_input`, `top_down_mover`, `health`, `hit_flash`, `camera_target`, `cues`; also `lifetime`, `despawn_outside`, `spawner`, `path_follower`, `platformer_controller`, `zone`, `animation`, `stats`, `cooldown`, `counters`, `flags`, `spawn_children`). React to events in data through `cues` and the `cue_rules` data kind, before writing a system: an action list per event (`damaged`, `killed`, `zone_entered`, `cooldown_elapsed`, or a game event brought in with `CuesOnEvent`); a reaction that needs a condition beyond a rule's tag filter is Rust. Declare game stats in the `stats` data kind. Declare tags in `assets/data/tags.json`, the manifest's `data.tags`; a prefab or a zone filter naming an undeclared tag fails the load. `ActionInput` reads the move actions and named slots (`"slots": { "jump": "jump" }`) into the entity's `Intent` each fixed step, which the movers take; an AI writes an `Intent` directly. `CameraTarget` marks what the camera follows. `Health` and `tungsten::kit::damage` apply hits, with the `damage_flash` shader and material from the manifest. A game system that belongs with the kit's joins a phase: `ensure_phases(schedule)`, then `Phase::Move.join(system(..))` in `fixed_update`, or `Phase::Present.join(..)` in `post_update`; a `post_update` system that moves a parent runs before `tungsten::kit::TRANSFORM_PROPAGATE_LATE`, and one that reads a child's position after it. The engine's genre fixtures, `crates/tungsten/tests/fixtures/kit/`, are the cookbook: a prefab per item in each genre.
- Register each system in `src/game.rs`'s plugin under a name, in a stage: `update` by default; `fixed_update` before `physics_step` for a system that drives bodies or reads input for movement: it runs once per fixed step (1/60 s of game time, zero or more times a frame), so a press moves the body on the next step, `just_pressed` there answers with the presses since the last step, none made while the game clock is paused or at scale 0, and it reads the events `fixed_update` sends, events from other stages in `update`; `post_update` with `before`/`after` against the engine's names in `tungsten::plugins` for one that runs around the physics sync, game feel or the camera. Systems in one stage run in the order they were added unless a constraint says otherwise; a typo in a constraint fails startup, which a harness test catches. Test each system on the engine's headless harness (`tungsten::testing::Harness`) in `tests/`.
- Read time from the `Time` resource: `delta()`, the game clock (scaled, zero while paused; the step inside `fixed_update`), for movement and animation, and `real_delta()` for anything that runs over a pause. Count cooldowns and lifetimes with `Timer`, ticked with the clock's dt. `DeltaTime` is deprecated.
- Read and write components through one query that names its data, `world.query::<(Entity, &A, Option<&B>)>()` or `query_mut_filtered::<&mut A, With<B>>()`, never a collected entity list and `get` per entity; spawn with `world.spawn_with((A, B, C))`, or `RigidBodyBundle::dynamic(..).with((..))` for a body, never a run of `insert`s; a teleport or respawn writes a body's `Position` and `PrevPosition` together, or it is drawn sliding from the old point; read a resource the engine inserts with `world.resource::<T>()`. The numbered `query2`/`query3_mut` functions are deprecated.
- Keep the player's choices in `Settings` (change, `tungsten::apply_settings(world)`, then `save()`) and progress in `SaveSlots` with a `SaveData` type, both in the game's user folder. A test that builds an `App` sets `config.game.user_folder = UserFolder::Off`, or `UserFolder::At` a fresh temp folder to test persistence, never the developer's own folder.
- Before a commit: `cargo test` and `cargo clippy --all-targets -- -D warnings`.
