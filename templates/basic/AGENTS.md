# AGENTS.md

Rules for this game's repository; `CLAUDE.md` imports this file.

## Layout

- `tungsten.json`, `input.json` and `assets/` sit in the game's folder, its working directory: run `cargo run` and `cargo test` from there.
- `src/main.rs` builds the app, turns `engine_exit` off and calls `game::register`, which adds the kit, the shell and the game.
- `src/shell/` holds the screens every game keeps: title, pause, game over, save and load, tabbed settings, keybindings, a confirm dialog, toasts, and the theme and widgets they share. Keep it as the template ships it and change it only to fix it, so a later template's shell can replace it whole.
- The shell calls the game through seven names, the seam, and nothing else: `game::GAMEPLAY` (the gameplay state's ID), `game::gameplay(RunStart)` (the state a run starts with), `game::BINDABLE_ACTIONS` (the Keybindings rows), `game::difficulty_note` (the picker's note) in `src/game.rs`, and `save::SaveGame`, `save::capture` and `save::summary` in `src/save.rs`. The game calls the shell back through `shell::game_over` and `shell::run`.
- `src/sample/` is the demo: a new game deletes it, with `tests/game/sample.rs`, writes its own gameplay and points the seam at it. The shell's tests that read the sample's entities follow the new gameplay.
- When the game passes about three components or two features, move each feature into `src/features/<name>/`: `mod.rs` holds its `Plugin`, `components.rs` and `systems.rs` the rest. `game.rs` only adds the feature plugins. A component two features share goes in `src/shared.rs`. A feature plugin registers its own prefab components, data kinds and systems, as a kit item does. The kit's scene names and data kinds are reserved: the registries fail startup on a duplicate.
- In the template itself, `src/shell/` stays within 2,400 lines of code and `src/` within 2,900, as `tokei` counts them (`D-187`); a feature past that belongs in a game. Scripts in `tools/` make its sounds and sprites.
- `tests/game/` holds the tests, one module per part: `sample`, `shell`, `saves`, `settings`, `keys`, `fit` (every screen at six windows and the scale extremes) and `visual` (the title's pixels, behind `TUNGSTEN_VISUAL_REGRESSION=1`).
- `tungsten check`, the engine's command line, loads `tungsten.json`, `input.json` and every file the manifest names as the game does, and reports every error with its file; `tungsten package` makes the players' archive in `dist/`.

## Saves and options

- The shell saves `save::capture`'s `SaveGame` to eleven slots of `SaveSlots`: `autosave`, written when the game pauses, quits to the title, exits and starts a run, and `slot_1` to `slot_10`, which the player saves to. `capture` returns `None` with no live run or a dead player, and nothing is saved then. Bump `SaveGame::SCHEMA` and extend `migrate` whenever `SaveGame` changes shape.
- A slot that fails to load, a newer build's or a damaged file, is never loaded or overwritten until the program restarts; the player can delete it.
- Keep the player's choices in `Settings`: change one, apply it with `shell::apply_settings(world)`, which keeps the mute while the window has no focus, then `save()`. Gameplay options are `GameOptions`, in a store of their own under the user folder's `options`.
- End the run with `tungsten::request_exit(world)`: the next frame is the last, with `Exiting` present, and the window's close button gives the same last frame, so one save system covers both.
- A test that builds an `App` sets `config.game.user_folder = UserFolder::Off`, or `UserFolder::At` a fresh temp folder to test persistence, never the developer's own folder.

## Input

- Read actions through `ActionMap`, never keys; bindings live in `input.json`, and the ones a player may rebind are listed in `game::BINDABLE_ACTIONS`. `ui_*` and `engine_*` actions are never listed, so the menus cannot be lost.
- Gameplay reads `RoutedInput`, what the UI left to the game. Every shell screen is a modal root, which takes every key and pad press, so a screen reads its own hotkeys from the raw `InputState`, only while no transition runs and no rebind is capturing.
- Only the top state's `update` runs, and it runs off the stack, so it cannot count the states: change the run through `shell::goto`. A press acts once: pause's Escape is both `ui_cancel` and `state_pause`, and pops one state.
- Screens act only when no transition runs; a scripted test waits out each transition before its next press.

## The kit

- Take generic gameplay from `tungsten::kit` before writing it: `game::register` adds `KitPlugins::set()` first, and a prefab composes the kit's components by their scene names, as `prefabs/player.json` does (`tags`, `action_input`, `top_down_mover` with acceleration, `aim`, `abilities`, `health`, `hurtbox`, `hit_flash`, `knockback`, `stats`, `camera_target`, `cues`), `bolt.json` (`linear_motion`, `hitbox`, `projectile`), the enemies (`contact_damage`, `oscillator`, `orbit`, `animation`), `gem.json` and the pickups (`pickup`, `cues`). The engine draws a sprite from its top-left at the entity's point, so the sprites are 32 px squares and every kit shape, body and the aim take `"offset": [16, 16]`.
- The rest of the catalogue: `lifetime`, `despawn_outside`, `spawner`, `path_follower`, `platformer_controller`, `zone`, `cooldown`, `counters`, `flags`, `spawn_children`, `follow`, `steering`, `speed_limit`, `wrap`, `stay_in_view`, `facing`, `character_animator`, `depth_sort`, `resist`, `shield`, `effects` (the `effects` kind, as `slowed`, `mend`, `heal` and `swift`), `abilities` (the `abilities` kind, as `shot`), `level` (the `curves` and `offers` kinds) and `ailment_threshold`.
- Motion: the kit moves a root's `Position`, or a body's `Velocity`, before the physics step, corrects it after the step (`wrap`, `stay_in_view`) and presents once a frame (`facing`, `character_animator`, `depth_sort`). A game system that moves what the kit moves joins the same phase and never writes that entity's `Transform`. `ActionInput` reads the move actions and named slots (`"slots": { "jump": "jump" }`) into the entity's `Intent` each fixed step, which the movers take; an AI writes an `Intent` directly. `CameraTarget` marks what the camera follows.
- Damage: `Health` takes hits through the damage pipeline, `tungsten::kit::damage` at once or a `DamageRequest` (a source, damage tags, a position, a knockback, a crit) queued for the step, past the entity's `resist` and `shield`, with the `damage_flash` shader and material from the manifest; `tungsten::kit::heal` restores it, and `health`'s `despawn_on_death` takes the dead after their `killed` cues. `tungsten::kit::knock_back` pushes an entity with a `knockback` back from a hit.
- Reactions: react to events in data through `cues` and the `cue_rules` data kind before writing a system: an action list per event (`damaged`, `killed`, `zone_entered`, `cooldown_elapsed`, `hit`, `healed`, `picked_up`, `expired`, `effect_applied`, `effect_expired`, `ability_used`, `level_up`, or a game event brought in with `CuesOnEvent`), whose `roll` draws drops from the `loot_tables` data kind, whose `effect` applies an `effects` entry to the subject or the other entity and whose `ability` uses or refills one of the subject's or the other's. The sample's `labels` rule floats a hit's damage only on an entity tagged `show.damage_numbers`, which the Damage numbers option sets on the player and the dummy. A reaction that needs a condition beyond a rule's tag filter is Rust.
- Data: declare game stats in the `stats` data kind and tags in `assets/data/tags.json`, the manifest's `data.tags`; a prefab or a zone filter naming an undeclared tag fails the load.
- Phases: a game system that belongs with the kit's joins a phase: `ensure_phases(schedule)`, then `Phase::Move.join(system(..))` in `fixed_update`, or `Phase::Present.join(..)` in `post_update`; a `post_update` system that moves a parent runs before `tungsten::kit::TRANSFORM_PROPAGATE_LATE`, and one that reads a child's position after it.
- The engine's genre fixtures, `crates/tungsten/tests/fixtures/kit/`, are the cookbook: a prefab per item in each genre.

## Rules

- Use the engine's public API, `tungsten::…`, and nothing else from its sources.
- Name assets by their ID in `assets/manifest.json`, never by file path (the engine's `D-009`).
- An entity kind the game places more than once, or that a level file places, is a prefab: a file under `assets/prefabs/` listed in the manifest's `prefabs`, with its sprite, tag and components. Register each component a prefab names, deriving `Deserialize`, in the plugin's `build`. Spawn one with `world.prepare_prefab(id, position)` and `.spawn(world)`, or from a system queue it with `CommandBuffer::spawn_prefab`; a state passes its `SceneEntity` through `.with(..)`, and a prefab queued from an entity with `CommandBuffer::spawn_prefab_from(entity, prepared)` takes that entity's `SceneEntity`, as the kit's `Spawner` spawns. A Tiled object whose class names a prefab spawns through `world.spawn_map_objects(map, origin)`.
- A definition several prefabs share (an effect, an item, a table) is a data entry: register its kind with `world.register_data_kind::<T>("<kind>")` in the plugin's `build`, list its file under the manifest's `data.<kind>`, and name it from a component's field as a `tungsten::core::DataRef<T>`, by ID or written in place; every ID a prefab or an entry names is checked at load, whatever the order.
- Draw through `Sprite` entities and tilemaps, which the engine draws by default, and screens through the UI tree. Add the game's own sprite batches, quads and text in its plugin's `build`, through `world.resource_mut::<Extracts>()` and `add_sprites`, `add_quads` or `add_text`: they draw after the defaults, in the order added. Replace a default (`replace_sprites`) only on purpose: the engine's `Sprite` entities and tilemaps stop drawing.
- Register each system in a plugin under a name, in a stage: `update` by default; `fixed_update` before `physics_step` for a system that drives bodies or reads input for movement: it runs once per fixed step (1/60 s of game time, zero or more times a frame), so a press moves the body on the next step, `just_pressed` there answers with the presses since the last step, none made while the game clock is paused or at scale 0, and it reads the events `fixed_update` sends, events from other stages in `update`; `post_update` with `before`/`after` against the engine's names in `tungsten::plugins` for one that runs around the physics sync, game feel or the camera. Systems in one stage run in the order they were added unless a constraint says otherwise; a typo in a constraint fails startup, which a harness test catches. Test each system on the engine's headless harness (`tungsten::testing::Harness`, or `UiHarness` for screens) in `tests/`.
- Read time from the `Time` resource: `delta()`, the game clock (scaled, zero while paused; the step inside `fixed_update`), for movement and animation, and `real_delta()` for anything that runs over a pause, such as a menu's animation or a toast. Count cooldowns and lifetimes with `Timer`, ticked with the clock's dt. `DeltaTime` is deprecated.
- Read and write components through one query that names its data, `world.query::<(Entity, &A, Option<&B>)>()` or `query_mut_filtered::<&mut A, With<B>>()`, never a collected entity list and `get` per entity; spawn with `world.spawn_with((A, B, C))`, or `RigidBodyBundle::dynamic(..).with((..))` for a body, never a run of `insert`s; a teleport or respawn writes a body's `Position` and `PrevPosition` together, or it is drawn sliding from the old point; read a resource the engine inserts with `world.resource::<T>()`. The numbered `query2`/`query3_mut` functions are deprecated.
- Keep what a run spawned by its handles, as the sample's `SampleRun` does: a replaced state's entities are despawned at the frame's end, so a query in that frame still sees them.
- Before a commit: `cargo test`, `cargo clippy --all-targets -- -D warnings` and `tungsten check`.
