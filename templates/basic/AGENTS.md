# AGENTS.md

Rules for this game's repository; `CLAUDE.md` imports this file.

## Layout

- `tungsten.json`, `input.json` and `assets/` sit in the game's folder, its working directory: run `cargo run` and `cargo test` from there.
- `src/main.rs` builds the app, turns `engine_exit` off and calls `game::register`, which adds the kit, the shell and the game.
- `src/shell/` holds the screens every game keeps: title, pause, game over, saves, settings, keybindings, a confirm, toasts and the boot splash, with their theme, built from `assets/ui/screens/` and `ui::widgets`, their handlers reading keys. Change it only to fix it, so a later template's shell can replace it whole.
- The shell calls the game through six names, the seam, and nothing else: `game::GAMEPLAY` (the gameplay state's ID), `game::gameplay(RunStart)` (the state a run starts with), `game::difficulty_note` (the picker's note) in `src/game.rs`, and `save::SaveGame`, `save::capture` and `save::summary` in `src/save.rs`. The game calls the shell back through `shell::game_over`, `shell::run`, `shell::run_meta` and `shell::request_autosave`; the sample also uses `shell::{play, top, stack, enter}`, `options::GameOptions` and the screens' IDs, which a later shell may change, and builds its HUD from `ui::widgets`.
- `src/sample/` is the demo: a new game deletes it, with `tests/game/sample.rs`, writes its own gameplay and points the seam at it. The shell's tests that read the sample follow the new gameplay.
- Each feature lives in `src/features/<name>/`: `mod.rs` holds its `Plugin`, its `GameState` and constants, `components.rs` its components and resources, `systems.rs` its systems; a part as big as the sample's HUD takes its own file. `game.rs` only adds the feature plugins. A component two features share goes in `src/shared.rs`. A feature plugin registers its own prefab components, data kinds and systems, as a kit item does. The kit's scene names and data kinds are reserved: the registries fail startup on a duplicate.
- In the template itself, `src/shell/` stays within 2,900 lines of code and `src/` within 3,400 (`tokei`, `D-199`). `tools/` scripts make its sounds, sprites and icon, which `build.rs` links.
- `tests/game/` holds the tests, one module a part: `sample`, `shell`, `saves`, `settings`, `keys`, `boot`, `fit` (every screen at six windows and scale extremes), `screens` and `visual` (the title's pixels, behind `TUNGSTEN_VISUAL_REGRESSION=1`).
- `tungsten check` loads every file the game reads; `tungsten package` makes the players' archive in `dist/`.

## Saves and options

- The shell saves `save::capture`'s `SaveGame` to `autosave_1`–`autosave_3` when the game pauses, quits to the title, exits, starts a run or asks through `shell::request_autosave` (once `capture` returns a save), unless Autosave is off (empty, one `migrate_step` refuses, the oldest, a damaged one), and to `slot_1`–`slot_10` when the player saves; `capture` returns `None` with no live run or a dead player.
- A save is the run's World: gameplay names what it keeps (`save::name`) once set up, `App::register_saved` adds a component, `capture` calls `capture_world` and a continued run spawns new, then `restore_world`. Bump `SaveGame::SCHEMA` and add a `migrate_step` step per change.
- A slot that fails to load is never loaded, nor written until a restart but by that order, a newer build's never; the player can delete it.
- Keep the player's choices in `Settings`: change one, apply it with `shell::apply_settings(world)`, which keeps the mute while the window has no focus, then `save()`. Gameplay options are `GameOptions`, in a store of their own under the user folder's `options`: the shell pauses and mutes, Screen shake sets the camera's `shake_scale`, and the game shows damage numbers itself, the sample by its `labels` rule's flag; each state names its song (`GameState::music`).
- End the run with `tungsten::request_exit(world)`: the next frame, the last, has `Exiting`, as a window close's does, so one save system covers both.
- A test that builds an `App` sets `config.game.user_folder = UserFolder::Off`, or `UserFolder::At` a fresh temp folder to test persistence, never the developer's.

## Input

- Read actions through `ActionMap`, never keys; bindings live in `input.json`, and its `labels` list the ones a player may rebind, the Keybindings rows; a `ui_*` or `engine_*` label fails the load, so the menus cannot be lost.
- Gameplay reads `RoutedInput`, what the UI left to the game. Every shell screen is a modal root, which takes every key and pad press, so a screen reads its own hotkeys from the raw `InputState`, only while no transition runs and no rebind is capturing.
- Only the top state's `update` runs, and it runs off the stack, so it cannot count the states: change the run through `shell::goto`. A press acts once: Escape, both `ui_cancel` and `state_pause`, pops one state.

## The kit

- Take generic gameplay from `tungsten::kit` before writing it: `game::register` adds `KitPlugins::set()` first, and a prefab names the kit's components by their scene names. The template's prefabs name `tags`, `action_input`, `top_down_mover`, `aim`, `abilities`, `health`, `hurtbox`, `hit_flash`, `knockback`, `stats`, `camera_rig` and `cues` (`player.json`); `linear_motion`, `hitbox` and `projectile` (`bolt.json`); `contact_damage`, `oscillator`, `orbit` and `animation` (the enemies); `spawner` (their spawners); `pickup` (the gem and pickups); `lifetime` (`spark.json`). The engine draws a sprite from its top-left at the entity's point, so the sprites are 32 px squares and every kit shape, body and aim take `"offset": [16, 16]`.
- The rest: `ailment_threshold`, `camera_target`, `camera_zone`, `cap`, `conversion`, `cooldown`, `counters`, `despawn_outside`, `effects`, `flags`, `follow`, `health_bar`, `level`, `looks`, `path_follower`, `penetration`, `platformer_controller`, `spawn_children`, `speed_limit`, `steering` and `zone`. Data kinds: `abilities`, `cue_rules`, `curves`, `damage_types`, `effects`, `interactions`, `loot_tables`, `offers`, `stats`, `tags` and `world_cues`.
- Motion: the kit moves a root's `Position`, or a body's `Velocity`, before the physics step, corrects it after the step (`wrap`, `stay_in_view`) and presents once a frame (`facing`, `character_animator`, `depth_sort`). A game system that moves what the kit moves joins the same phase and never writes that entity's `Transform`. `ActionInput` reads the move actions and named slots into the entity's `Intent` each fixed step for the movers; an AI writes an `Intent` directly.
- Damage: `Health` takes hits through the damage pipeline, `tungsten::kit::damage` at once or a `DamageRequest` queued for the step, past the entity's `resist` and `shield`, flashing through the engine's `damage_flash` material; `tungsten::kit::heal` restores it, and `health`'s `despawn_on_death` takes the dead after their `killed` cues.
- Reactions: react in data through `cues` and the `cue_rules` data kind before writing a system: an action list per event (`damaged_part`, `damaged`, `killed`, `zone_entered`, `cooldown_elapsed`, `hit`, `healed`, `picked_up`, `expired`, `effect_applied`, `effect_expired`, `ability_used`, `ability_refused`, `ability_ready`, `ability_held`, `ability_released`, `culled`, `level_up`, `jumped`, `air_jumped`, `jump_refused`, `landed`, `arrived`, `departed`, or a game event from `CuesOnEvent`), whose `roll` draws a `loot_tables` entry, `effect` applies an `effects` entry and `ability` uses or refills an ability, on the subject or the other entity. A reaction past a rule's filters is Rust.
- Data: declare game stats in the `stats` data kind and tags in `assets/data/tags.json`, the manifest's `data.tags`; a prefab or zone filter naming an undeclared tag fails the load.
- Phases: a game system that belongs with the kit's joins a phase: `ensure_phases(schedule)`, then `Phase::Move.join(system(..))` in `fixed_update`, or `Phase::Present.join(..)` in `post_update`; a `post_update` system that moves a parent runs before `tungsten::kit::TRANSFORM_PROPAGATE_LATE`, and one that reads a child's position after it.
- The cookbook, in the engine repository at `Cargo.toml`'s tag: `crates/tungsten/tests/fixtures/kit/` and `api/tungsten-kit-components.txt` (every field). The engine's own, `rigid_body` (with `layers` and `mask`), `particle_emitter`, `tilemap` and the rest, are in the rustdoc of `tungsten::core::component_registry`.

## Rules

- Use the engine's public API, `tungsten::…`, and nothing else from its sources.
- Name assets by their ID in `assets/manifest.json`, never by file path (the engine's `D-009`).
- An entity kind the game places more than once, or that a level file places, is a prefab: a file under `assets/prefabs/` listed in the manifest's `prefabs`. Register each component a prefab names, deriving `Deserialize`, in the plugin's `build`. Spawn one with `world.prepare_prefab(id, position)` and `.spawn(world)`, which returns the entity, or queue it with `CommandBuffer::spawn_prefab` while a query borrows the world; a state passes its `SceneEntity` through `.with(..)`, and a prefab queued from an entity with `CommandBuffer::spawn_prefab_from(entity, prepared)` takes that entity's `SceneEntity`. A Tiled object whose class names a prefab spawns through `world.spawn_map_objects(map, origin)`, a room in `rooms` through `world.spawn_room(id, origin, &with)`; a scene file through `tungsten::asset_loader::load_scene`, then `spawn_scene`.
- A definition several prefabs share (an effect, an item, a table) is a data entry: register its kind with `world.register_data_kind::<T>("<kind>")` in the plugin's `build`, list its file under the manifest's `data.<kind>`, and name it from a component's field as a `tungsten::core::DataRef<T>`; every ID a prefab or an entry names is checked at load.
- Draw through `Sprite` entities and tilemaps, which the engine draws by default, and screens through the UI tree. Add the game's own sprite batches, quads and text through `Extracts` (`add_sprites`, `add_quads`, `add_text`) in its plugin's `build`, drawn after the defaults; replace a default (`replace_sprites`) only on purpose. A run builds its `PostStack` whole; the shell takes its Bloom out while that option is off.
- Register each system in a plugin under a name, in a stage: `update` by default; `fixed_update` before `physics_step` for a system that drives bodies or reads input for movement: it runs once per fixed step, and `just_pressed` there reads the presses since the last step; `post_update` with `before`/`after` against the engine's names in `tungsten::plugins` for one that runs around the physics sync, game feel or the camera. Systems in a stage run in the order added unless constrained; a typo in a constraint fails startup. Test each system on the engine's headless harness (`tungsten::testing::Harness`, or `UiHarness` for screens) in `tests/`.
- Read time from the `Time` resource: `delta()`, the game clock (scaled, zero while paused; the step inside `fixed_update`), for movement and animation, and `real_delta()` for anything that runs over a pause, such as a toast. Count cooldowns and lifetimes with `Timer`, ticked with the clock's dt.
- Read and write components through one query naming its data, `world.query::<(Entity, &A, Option<&B>)>()` or `query_mut_filtered::<&mut A, With<B>>()`, never entities collected from a query to `get` each; spawn with `world.spawn_with((A, B, C))`, or `RigidBodyBundle::dynamic(..).with((..))` for a body, never a run of `insert`s; a teleport or respawn writes a body's `Position` and `PrevPosition` together, or it is drawn sliding from the old point; read a resource the engine inserts with `world.resource::<T>()`.
- Keep what a run spawned by its handles, read with `world.get`, as the sample's `SampleRun` does: a replaced state's entities are despawned at the frame's end, so a query in that frame still sees them.
- Before a commit: `cargo test`, `cargo clippy --all-targets -- -D warnings` and `tungsten check`.
