## 2. Design

### 2.1 Scope and the shell's plumbing

S-72 lands: the settings screen is a file of keyed rows with their kinds and ranges, its values bound by name. The shell stays on its own change machine until 7.11 (A14), so a converted state builds its file with `screen_build::build`, gives the root to `enter` as today, refreshes its bindings where its `refresh` runs now and handles each control by its key. The action vocabulary (§2.3) runs in `tungsten::screens::DataScreen` (§2.6), which `render --screen` and a game's own data screens use; the shell's files name no action until 7.11 ports it (Q2). §5.11's "where that shrinks them" is measured: each conversion step lowers the shell's `tokei` count or is skipped.

### 2.2 The file

One JSON object per screen, `assets/ui/screens/<id>.json`, listed in the manifest's `ui_screens` as `{ "<id>": { "path": "ui/screens/<id>.json" } }` (`D-009`); entries resolve, refuse a missing file and merge as `ui_themes`' do (A2). `ScreenFile::from_json` reads `version` first (1; any other value fails before the rest, A4), then the model through `serde_path_to_error`, so every error names its field (`root.children[2].captoin`), then the structural checks with paths. Unknown fields fail everywhere.

- **Top:** `version` and `root`, a root node.
- **Root nodes:** `screen` is `widgets::screen`: a modal scrim root on the popup layer and its card, `width` a length; its `children` go in the card, `card` (`layout`, `overrides`) edits the card, and `over` holds children under the root after the card (the title's footer). `root` is a bare root: `layer` (`game` or `game_popup`), `modal` (default false), `layout`, `overrides`, `children`.
- **Child kinds:** `group`, `row`, `column` (`widgets::group`, `row`, `column`) and `panel` hold `children`; `label`, `heading` (`centred`), `display` (`style`), `note`, `small` and `prompt` (`template`) are text; `button` (which also holds `children`, as the title's Continue holds its age line), `choice_row`, `toggle_row`, `slider_row` (`range`: `min`, `max`, `step`; `readout`, a text binding) and `tab_rail` (`tabs`: `key`, `caption`) are controls; `meter` (`width`, `height`, `color`); `mount` (`mount`, a mount name); `repeat` (`key`, required; `rows`, a provider; `row`, the node built per row).
- **Every node:** `key` (`set_key`); `layout`, fields over the builder's layout: `direction`, `width`, `height`, `min_*`, `max_*`, `padding`, `margin`, `gap`, `align_items`, `align_self`, `justify_content`, `anchor` (`corner`, `offset`); `overrides`, the theme file's overrides object, colours as `#rrggbb`, `#rrggbbaa` or a token's name resolved against the tree's theme at build; `style`, a named text style; `mono` and `danger` (`widgets::mono`, `danger`); `bind` (§2.3); `on` (§2.3).
- **Text:** a text node takes exactly one of `text` (a literal), `bind.text` (a binding) or, in a `repeat`'s `row`, `field` (the row's field); a button's caption is its text; a row's `caption` is literal and a choice row's value takes `bind.text`.
- **Values:** a length is a number in UI units, a size name (`Theme::size` over `widgets::size`'s defaults) or `spacing.xs` to `spacing.xl`; a sizing is a length, `auto`, `fill` or `<n>%`, and a `min_*` or `max_*` also `none`; edges are a number or an object of `top`, `right`, `bottom`, `left`, `x`, `y`. Numbers are finite; a range's `min` is below its `max` and its `step` positive.
- **Checks in the file:** keys are names without a `/`, unique in a file, and the keys inside a `repeat`'s `row` unique within that row; the `/` is reserved for the keys a repeat builds (§2.3); a `field` only inside a `repeat`'s `row`; an `on` only on a control; `card` and `over` only on `screen`.
- **Version:** 1. A kind or a field added later keeps version 1, since every version-1 file still reads; a changed meaning or a removed field takes version 2 and a refusal of 1 that names it.

Not in version 1: images, scroll panels beyond the card, per-row bindings other than `field`, and anything conditional (Q7).

### 2.3 Bindings, providers, mounts and actions

`UiBindings`, a core `World` resource (`UiBindings::of(world)` inserts it), holds the game's names, each registered in a plugin's `build` with a `&'static str` and a plain `fn`, a second registration replacing the first:

| Kind | Signature | Written to |
| --- | --- | --- |
| `bind.text` | `fn(&World) -> String` | a text node, a button, a choice row's value, a slider row's `readout` (`set_plain_text`) |
| `bind.value` | `fn(&World) -> UiValue` | a toggle (`Bool`), a slider (`Number`) or a tab rail (`Number`, the selected tab's index: its bar shown, the others hidden) |
| `bind.fill` | `fn(&World) -> f32` | a meter (`Meter::set`, its `color`) |
| `bind.visible` | `fn(&World) -> bool` | any node: `Visible`, else `Collapsed` (`widgets::show`) |
| `bind.enabled` | `fn(&World) -> bool` | any node (`set_enabled`) |
| `rows` | `fn(&World) -> Vec<UiRow>` | a `repeat`: `UiRow { key, fields }`, the fields a `BTreeMap<String, String>` |
| `mount` | `fn(&mut World, WidgetId)` | a `mount` node, which the game fills |
| `action` | `fn(&mut World, UiAction)` | an `on` action; `UiAction { key, row, value }` |

`enabled` joins §5.11's five because every screen the shell converts enables controls by state (pause's Save and Load, settings' Size, Apply, the frame cap and Difficulty, the title's Continue and Load) (Q1). No binding takes arguments or combines with another: a screen's state that a binding shows lives in a resource its state owns (`StateStack::own_resource`, `D-235`), the settings' pending picks, held slider and selected tab among them, and a binding takes that resource's absence as the screen's opening state, so a file opened alone (`render --screen`) shows what its state would show on entering.

A repeat's rows and their controls have one identity each: a built row's node is keyed `<repeat key>/<row key>` and a keyed node inside it `<repeat key>/<row key>/<its key>`, so focus and `find_key` tell them apart and no file key can equal one (§2.2's `/`). A row control's action gets `UiAction { key, row: Some(<row key>), value }`, `key` its own key in the file (the repeat's for the row's node). A provider's row key that repeats or holds a `/` warns once, and that row builds unkeyed and actionless. A mount's keys are the game's: a duplicate under the root warns, as `set_key` does (`tree.rs:1556-1566`).

`on` takes one action: `"pop"`, `{"push": "<id>"}` (a `ui_screens` ID or a registered screen name), `{"action": "<name>"}` (a button, a choice row, or a toggle or slider called with its value) or `{"setting": "<name>"}` (a toggle or slider). Settings: `vsync` (bool), `master_volume`, `music_volume` and `effects_volume` (0 to 1), `ui_scale` and `text_scale` (factors); a control with a setting shows it as set, else as it runs, unless `bind.value` names another, and a change writes `Settings` and calls `tungsten::apply_settings`. Anything else reaches the game as the widget's key in `UiEvent` (A10).

### 2.4 Building and refreshing a screen

`ui::screen_build` (core), on `UiScreenRegistry`, `UiBindings` and `UiTree`:

- `build(world, id) -> Option<BuiltScreen { root, card }>`: a new root built from the file through 7.17's builders, in file order; the live screen recorded in `UiScreens`, a core resource (never a `UiTree` field, A19): its ID, root, revision, bound nodes, repeats and keyed actions; then each mount called with its node, then `refresh`. An unknown ID returns `None`, warning once; a name the World lacks warns once and is skipped, the check refusing it (§2.7).
- `refresh(world, root)`: every binding of that screen read with `&World` and written compare-on-write (A11), so equal values mark nothing; a `repeat`'s rows rebuilt only when their keys or fields changed. It never writes the value of the control the router has captured, from its press to its release or cancel: `UiRouter::captured`, a read-only accessor over the router's own field, which outlives the pressed look a pointer leaving the control drops (`route.rs:682-686`, `:855-858`). So a drag keeps its draft across frames, still ones and ones outside the slider included, and commits from it (`route.rs:1412`), the next refresh after the commit reading the stored value. Its owner calls it: a shell state where its `refresh` runs today, a `DataScreen` every frame.
- `action(world, root, key)`, `revision(world, root)` and `node(world, root, key)` (`find_key` under the root) for the owner. Entries whose root is gone are pruned at the next `build` or `reload`.

### 2.5 Reloading

`screen_build::reload(world, id)`, from the asset loader's reload (step 5), for every live screen built from `id`: whether focus lies under the root, and the focused widget's key, noted; every child of the root removed (A12) and rebuilt from the new file; the root's own `layout` and `overrides` edited in place; mounts called again; bindings refreshed; the revision raised. Focus moves only when it lay under the root: to the node with the noted key, else the root's first that can take focus. Focus elsewhere stays, since a covered screen is shown and frozen and `can_focus` does not read freezing (`state.rs:549`, `focus.rs:92`). A data screen notes its opener's key with its `WidgetId` (`screens/mod.rs:210`) and, when its revision rises, finds the opener again by that key, so a reload while covered still returns focus to the opener on resume (`:282-290`). The root is kept, so its state's ownership, cover, tracks and slide stand; a changed `layer` or `modal`, or a root of the other kind, waits for the next build and warns once. Rebuilt nodes take new IDs, so a state reads a node by key (`node`), never across a revision, and a state that edits its screen after the build (game over's hidden card and its gap) makes those edits again when the revision rises; the shell's converted states keep only roots. A file that fails to parse keeps the previous file and its screens, one error logged, as a theme's (A6). Reloads arrive through the watcher's channel and apply in `App`'s reload pass on the main thread (the two-thread rule).

### 2.6 Data screens in `tungsten::screens`

- `screens::open(world, id)`: a registered name as today, else a `ui_screens` ID pushes `DataScreen::new(id)`; it inserts `Screens`, `ScreenRegistry` and `Toasts` when absent, as `ScreensPlugin` does, so a script opens a file in a game without the plugin. A data screen's root is a modal root on the popup layer (a `screen`, or a `root` with `layer: game_popup` and `modal: true`): roots stack by layer (`tree.rs:284-288`), `screens::pop` closes the front-most shown modal root and only the top state's `update` runs (`screens/mod.rs:127`, `state.rs:416`), so a non-modal root, or a modal one on the game layer under a popup, would close the screen under it and leave its slide unfinished. `open` refuses another file with a warning naming it, and the check refuses a `push` naming one; a game's own state may still `build` any file.
- `DataScreen`: its `id()` is the screen's ID, interned once per ID in `UiScreenRegistry` (as `render/text/fonts.rs:83` interns family names), since `StateId` is `&'static str` (A13; Q8). `on_enter` builds the file and hands its root to `ModalScreen::adopt` (the slide, `own_root` with `RootCover::Show`, the toasts raised), split out of `ModalScreen::open`, which keeps its behaviour. `update`: `ModalScreen::update`'s closing, idleness and cancel; then one event per control kind runs its action, since a toggle's activation sends `Activated`, `ValueChanged` and `ValueCommitted` and a slider's release can send `ValueCommitted` and `Activated` (`route.rs:1361-1377`, `:922-929`): a button's and a choice row's on `Activated`; a toggle's and a slider's on `ValueCommitted` alone, with its value (a slider's at its drag's end or a step, so a scale is not applied under the pointer). Actions: `pop` → `screens::pop`, `push` → `screens::open`, `action` → the registered fn, `setting` → §2.3. Then `refresh`. `on_resume` focuses the opener.

### 2.7 Loading, the check and the schemas

- **Loading:** `load_ui_screens(manifest, world)` parses every entry in sorted ID order into `UiScreenRegistry` and records paths in `UiScreenPaths`, a file that fails failing the load as a theme's does. It runs inside `LoadUnit::Themes`' arm after the themes and in `Harness::load_manifest`, so the load plan's units stay as they are and 02's `boot` digest holds; it inserts its two resources only when the manifest has entries, and every reader takes their absence as none, so a manifest without screens allocates nothing more and `guards_boot` holds (A5).
- **The check:** a stage after the themes: each file parsed, errors named `ui screen '<id>': <field>: <message>`; then `ScreenFile::check(&ScreenNames)` (core, shared with tests) against the World the plugins built: bindings of the right kind, providers, mounts and actions in `UiBindings`; text styles built in or in a loaded theme; size names in a theme's `sizes` or `widgets::size`'s defaults; colour tokens; `push` targets among `ui_screens` IDs and `ScreenRegistry` names; settings in the vocabulary. `manifest_files` lists the screen files (step 1), so none is checked as a scene (A7).
- **Canonical form:** `ScreenFile::to_canonical()`: the model as JSON with defaults left out, keys sorted, arrays in order, two-space indents, whole numbers without a fraction and others in the shortest form that reads back as the same `f64`, and a final newline. `from_json(to_canonical(f)) == f`, and `to_canonical` is idempotent. The repository's screen files are canonical, held by a `tungsten-cli` test beside the embedded template's; a game's files are not checked for it (Q9).
- **Schemas:** `screen_file::json_schema()` and `theme_file::json_schema()` (draft 2020-12, §5.9's Waits naming theme files): `additionalProperties: false` on every object, one `$defs` entry per node kind chosen by its `kind`, the overrides and text objects shared, enums for kinds, layers, alignments, corners and settings; the game's names as strings. One table of each kind's fields drives both §2.2's structural check (a field another kind takes fails with its path) and the schema's per-kind `properties`. A test holds each schema to its model: for every object the model reads, the fields serde names when it refuses an unknown one (`expected one of …`) are the schema's `properties` (for nodes, their union over the kinds), and the kinds are the schema's. `tungsten schema ui_screen|ui_theme [-o <file>]` prints or writes one from the CLI's own build (A21); another name exits 2 naming both.
