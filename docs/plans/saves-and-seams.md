### 2.2 Save identities

- **`SaveId(u64)`** in core. `SaveId::authored(name)` is `D-222`'s: the name's 32-bit FNV-1a hash with bit 31 set, so 01's IDs carry over at 7.13. A run's spawns take the run's counter, below bit 31, which refuses to reach it. Authored names are unique across a game's areas (Q11).
- **`Saved`**, one core component, holds an entity's `SaveId`, its area (none for a global entity) and, for a run's spawn, its prefab. A `SaveState` resource holds the counter, the areas, each named entity's baseline (§2.5), the kept areas and the pending references (§2.7). It exists from the World's first naming: a World where nothing was named has none, and nothing in it pays for saves.
- **Naming.** `save::name(world, entity, area, name)` names an entity the game spawned, once its setup from the run's start (a difficulty) is done and before anything random or the run's play touches it; it records the entity's baseline (§2.5). A name a live entity holds is refused; a dead one's is free, so an enemy that returns takes its name again. `World::spawn_area` names a map's named classed objects (§2.7).
- **A run's spawns** (Q12). A spawn from a source that is `Saved` (`CommandBuffer::spawn_prefab_from`, as the kit's abilities, spawners and cues spawn) takes the next ID at the flush, the source's area and its prefab's ID. The prefab's ID travels to the flush only when `World::prepare_prefab` found a `SaveState`, so a World that never named spawns exactly as today: no component, archetype move or allocation more (§5). A spawn with no saved source is not saved, nor one prepared `unsaved()` (`PreparedPrefab::unsaved`), which the kit's `SpawnChildren` uses for its children (Q5) and a game for presentation (Q6).
- **ID order.** IDs follow the buffer's queue order, so a path that spawns from a saved source queues in save order: the kit's sorts by save ID, `Spawner`'s due spawns and `Cooldown`'s events (§2.10), so two spawners or two cooldowns' cues due in one step give their spawns the same IDs in a world whose archetype rows differ.
- **Order keys.** `save::order_key(world, entity)` gives `(false, id)` for a saved entity and `(true, index)` for the rest; `save::saving(world)` tells whether the World has save state.

### 2.3 The registry

- **One line.** `World::register_saved::<T>(name)` for a component `T: Serialize + DeserializeOwned + 'static`, `register_saved_resource::<T>(name)` for a resource, and `App::register_saved` and `App::register_saved_resource` in a game's `main.rs`: version 1, no migration, no references. Names follow the component registry's rule (`[a-z][a-z0-9_]*`), one name per type and one type per name in each of the two maps; a name or type registered with another panics, the same pair again is a no-op (as `D-153`'s registry).
- **Options.** `register_saved_with` and `register_saved_resource_with` add a version, migration steps (`from` to `from + 1`, on a JSON value) and a reference codec: `save` writes the value's entity references as save IDs (an entity without one is dropped and counted), each under the key it hangs on in the value, `load` sets them from save IDs, reporting those it could not resolve, and `keys` lists the keys the value holds now (§2.7).
- **Core's own,** each through a saved form of its own: `position`, `velocity` and `spin` by `PhysicsPlugin`; `transform` and `visibility` by `App`. `RigidBody`, `Collider` and presentation come from the prefab (Q7).

### 2.4 The format

A `WorldSave` is plain JSON the game's `SaveData` type holds as a field; the envelope, schema and slots stay `D-160`'s. Its keys sort, a run's spawns go by ID and floats print shortest, so two captures of one world are byte-equal.

```json
{
  "format": 1,
  "next_id": 57,
  "versions": { "components": { "health": 1, "position": 1 }, "resources": { "counters": 1 } },
  "global": { "named": {}, "gone": [], "spawns": [] },
  "areas": {
    "sample": {
      "named": { "gem_1": { "components": { "position": [430.0, 344.0] } } },
      "gone": ["gem_0"],
      "spawns": [ { "id": 12, "prefab": "bolt", "components": { "position": [610.0, 340.0] }, "refs": { "source": 2895758080 } } ],
      "tiles": { "level": { "layers": ["ground", "walls"], "edited": [[1, 4, 7, "rock_wall"], [1, 6, 7, null]], "damaged": [[1, 5, 7, 12.5]] } }
    }
  },
  "resources": { "counters": { "gems": 1 } }
}
```

- A named record holds `components` (patches, §2.5), `removed` (components the fresh spawn had and the run took off) and `refs`; a spawn record holds its `id`, `prefab`, `components` in full, every registered one it had, and `refs`. `versions` names each saved component's and each resource's version once, in two maps, since a component and a resource may share a name. `tiles` holds, per map, its layers' names at the capture, each edited cell's layer, column, row and tile by its sprite ID (null for none), since the loader numbers tiles densely in Tiled's order, and each damaged cell's health.

### 2.5 Changes over the fresh spawn (S-3)

- A named entity's baseline is its registered components, serialized, when it was named. A capture writes, per component, a patch: for an object, each key whose value differs from the baseline's, an object key's own patch recursively, with `"-"` listing at each depth the keys the baseline had and the value no longer writes (a field a serde form skips when off); arrays and other values go whole when they differ. So a modifier added to one stat patches that stat's `modifiers` alone, and its `base` stays the prefab's (`Stats` serializes as a map of stats, `crates/tungsten-kit/src/foundation/stats.rs:186-208`). A restore merges the patch over the fresh spawn's value and deserializes the result.
- So an old save carries only what its run changed: a retuned field the run never changed reaches it unmigrated, and a changed one keeps the save's. A run's spawns go in full: they have no fresh spawn to lay changes over.
- A fresh spawn must be the same in every run of its level from the same start, since a restore merges over it: a value drawn at random or set by play after the naming lands in the patch.
- A migration step sees a patch for a named entity and a whole value for a spawn, so it rewrites the fields it is given and assumes none is present.

### 2.6 Capture and restore

- **`save::capture_world(world) -> Result<WorldSave, CaptureError>`**: one call. Each `Saved` entity's registered components, references by save ID, the named entities gone since they were named, each loaded area's tiles, each registered resource whole, the counter and the kept areas (§2.7). It runs at a frame boundary (Q17): it fails with `CaptureError::Queued` while the World's command buffer holds commands, since a queued spawn's cost is already paid (a `Spawner`'s count), and otherwise only when a value's own `Serialize` does. The shell's due autosaves and slot saves capture in `PreUpdate` after the flush (`D-197`), its Quit and Load from screens over a run whose clock gameplay holds while covered (`templates/basic/src/shell/pause.rs:3`), and a script action runs before `PreUpdate` (`crates/tungsten/src/app.rs:1449`); the kit's queued requests are saved resources (Q4), so a live run captures at each.
- **`save::restore_world(world, &save, with) -> Result<RestoreReport, RestoreError>`**: one call, into a world the game has spawned as a new run, its entities named; `with` is the bundle a restored spawn takes, as a prefab spawn's `with` (the template passes its `SceneEntity`). It checks first and changes nothing on an error: the format, a version newer than the registry's, each value migrated a step at a time from its saved version and merged, each spawn's prefab prepared, each tile record against its map and its tiles' sprite IDs against the tileset. Then: each loaded area's map put back as inserted and its tiles written (§2.7); the gone despawned; each named entity's patches and removals applied, a body's moved position through `physics::teleport`; each spawn spawned from its prefab at its saved position, its saved components and `Saved` inserted and every registered component its record lacks removed, so a spawn comes back as it was; resources replaced; the counter set; then references resolved by save ID in a second pass, once every entity exists; then each restored body overlapping a solid set out at its free spot (§2.8).
- **Forgiving.** A component name the registry lacks, a prefab the manifest lacks, a named record whose entity the level no longer has, and a tile edit past its map's layers or cells, on a layer whose name changed or naming a sprite its tileset lacks are dropped, a line each in the report, so a save outlives a content change; a named entity the save lacks stays fresh, so adding to a map never touches a save.

### 2.7 Areas and their tiles

- **An area** is a level reference: a manifest tilemap ID for `World::spawn_area(map, origin)`, which puts the map back as inserted (`TilemapRegistry::revert`, a copy kept at `insert`), spawns its instance and its objects and names each named classed object in it; or a name a game gives its code-built level (the template's `sample`). An unnamed classed object spawns unsaved. A new run's area therefore starts on the map as its file has it.
- **Kept areas.** A restore keeps each area the world has not loaded, migrated to the registry's versions, and a capture writes it back. `save::enter_area(world, level)`, after the game spawns the area, applies its kept record as a restore does and resolves the references into it; 8.1 calls it.
- **Pending references** (Q18). A reference into a kept area stays its save ID, kept beside its holder with the key its codec hangs it on (an effect instance's serial, a hitbox's activation count, a touch's target), and the capture writes it as it came until the area loads. At each capture and at the entry, one whose key the holder no longer has is dropped, so a hitbox rearmed meanwhile never takes its old target back; the first resolve replaces the rest. Nothing in a loaded area may need one before (§5.5).

### 2.8 The free spot (S-2)

`physics::free_spot(world, entity) -> Option<Vec2>`: for a body whose collider overlaps a solid past `linear_slop`, the nearest position where it overlaps none, searched outward in rings of a quarter cell to eight cells, ties up, then right, down, left; a cell is the tile size of the map it overlaps, 16 px where it overlaps none. Solids are the full collision cells of the layers its mask meets, read from the maps and their instances, and static bodies those layers meet; one-way and slope cells are not (Q8). It reads the grids, not the query index, which a restore's fresh bodies are not in yet (A11). A restore runs it on each body it placed; none in reach leaves the body where it was, a line in the report.

### 2.9 Slots a schema at a time, and stamped saves (S-43, S-101)

- `SaveData::migrate_step(from, data)` rewrites a save from `from` to `from + 1`; `migrate`'s default runs it once per schema up to `SCHEMA`. A type that overrides `migrate` keeps its own, so 01 and the template load as before until steps 6 and 9.
- `SaveSlots::save_stamped(slot, &data, &stamp)` writes a save under a given schema, engine version and time, through `write_atomic`, for tests.
- Step 6 turns 01's arms into `migrate_step`'s, each its own schema's change, with its tests unchanged.

### 2.10 The kit

- **Saved components.** Each kit plugin registers, in its `build`, its components that hold state play changes, under its scene names, and its resources (`KitRng`, `Counters`, `Flags`). `Lifetime` and `Spawner` gain saved forms of their time; `Source` saves as a reference alone. Reference codecs: effect sources by serial, a hitbox's hit targets under an activation count it gains (saved, raised by `arm` and `rearm`, `crates/tungsten-kit/src/overlap/hit.rs:884-892`), a contact's touches with their times by target, `Source`. `foundation/saved.rs` names the described components the kit does not save, each with its reason (rule data a prefab gives, presentation, the hierarchy (Q5)), and a test holds every described component to exactly one of the two.
- **Queues.** The damage, heal and effect requests gain saved forms, damage kinds by name, and their queues register as saved resources whose targets and sources are references (Q4), so a request queued after a step's resolve resolves once after a load.
- **Children.** `SpawnChildren` prepares its children `unsaved()`, so a saved parent's children come back once, from the parent's fresh spawn (Q5).
- **Orders by save ID (S-59).** The 18 sorts of A4 that order a step's work, `Spawner`'s due spawns and `Cooldown`'s elapsed events (sent in query order for a cooldown without jitter, `crates/tungsten-kit/src/lifecycle/cooldown.rs:408-440`, which cues spawn from), key through one helper in `foundation/saved.rs`: `save::order_key` while `save::saving(world)`, read once a sort, and the entity's index otherwise, so the kit's pin, 01 and every World that never named keep today's orders. The two sorts that index a lookup keep entity index with their lookups, and the hierarchy's queued children keep theirs (Q5). Events from physics (triggers, zones) keep the step's order (Q3).
