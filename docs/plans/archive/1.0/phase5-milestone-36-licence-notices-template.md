## 2. Design

**Notices (step 1).** Two halves, split where the data lives.

- *Collect*, in each build job: `release.py licenses <target> --out target/licenses.json` runs `cargo fetch --locked --target <target>`, then `cargo metadata --locked --format-version 1 --filter-platform <target>`, and walks `resolve.nodes` from the shipped packages (the `examples/*` members `examples()` returns, plus `tungsten-launcher`) along normal edges only (Q2). For each registry crate it records name, version, `license`, `license_file`, `repository` and the text of every root-level file whose name starts with `LICEN[CS]E`, `COPYING`, `COPYRIGHT`, `UNLICENSE` or `NOTICE` (any case, any suffix), plus `license_file`. It also records the toolchain's `COPYRIGHT-library.html` and `rustc --version`. A missing crate source or standard-library notice fails it. The `cargo` call is a parameter, as `package`'s splitter is (`D-120`), so tests inject fake metadata.
- *Decide and write*, in `package` and in `release.py notices <licenses.json> --out <dir>` (the same code without the archive): each crate needs an entry, one licence text per licence of the chosen alternative. An alternative is one disjunct of the expression (`/` read as `OR`, `AND` binding tighter, `WITH` kept with its licence); alternatives are tried in the order of Q4; a licence matches a file by marker phrases of its standard text. `NOTICE` files always ship with the crate. A crate in `licenses/clarifications.json` takes the texts listed there, and fails when its version differs from the one the entry records as checked (Q5). A crate with no entry fails the call, naming every such crate. `package` reads `<bin_dir>/licenses.json` and fails without it.
- *Bundled works:* content a crate compiles in under another licence than its own, which crate metadata cannot show (A27). A crate's `bundled` list in `clarifications.json` names each work with its licence, text, source and the crate version checked, and the notices write it under the crate whatever the crate's own licence; at `0a1f32f` that is `sctk-adwaita`'s Cantarell Regular (OFL 1.1), Linux only. The collector also records the font files (`.ttf`, `.otf`, `.ttc`, `.woff`, `.woff2`) each shipped package carries, and `notices` fails on a crate that carries one with neither a `bundled` entry nor a `fonts_reviewed` note saying why it is not compiled in (A27's four test and example cases). Other bundled data stays a manual check, which `docs/releases.md` describes (step 2).
- *Archive layout:* the root gains `THIRD-PARTY-NOTICES.txt` and `THIRD-PARTY-NOTICES-rust-std.html`. The text file holds a header (Tungsten's own code is MIT: `LICENSE`; font licences sit beside the fonts under `assets/fonts/`; the standard library's notices are the HTML file), the embedded works with their texts, an index of crates (name, version, expression, the licence used, `https://crates.io/crates/<name>/<version>` and the repository, which also tells MPL users where the source is), then each distinct licence text once, under the crates that use it. `README.txt` names both files.
- *Embedded works* are a table in `release.py`: SMAA (lookup textures and ported shaders) with `crates/tungsten-render/src/assets/smaa/ATTRIBUTION.md`; step 3 adds the engine font with `crates/tungsten/assets/fonts/OFL.txt`. A listed file that is missing fails `notices`.
- *Workflow:* the build job adds a `Collect licence data` step after the build and `target/licenses.json` to the upload list, so it lands at the artifact root, where `package --bin-dir` finds it. `just notices` collects and writes both targets into `target/notices/` and joins the release checks (step 2).

**The engine font (step 3).** API sketch, the only new public item:

```rust
// crates/tungsten/src/engine_font.rs (module private; lib.rs: pub use engine_font::ENGINE_FONT_ID)
/// Font ID of the engine's embedded JetBrains Mono Regular, the default for
/// the HUD, the systems overlay and the inspector (`D-123`). Registered when
/// the renderer starts, before the manifests; a manifest face with this ID
/// replaces it for engine text.
pub const ENGINE_FONT_ID: &str = "engine_mono";
pub(crate) const ENGINE_FONT: &[u8] = include_bytes!("../assets/fonts/JetBrainsMono-Regular.ttf");
pub(crate) fn register(renderer: &mut Renderer) { renderer.load_font(ENGINE_FONT_ID, ENGINE_FONT.to_vec()); }
```

`App`'s `resumed` calls `engine_font::register` right after `Renderer::new` succeeds, before `load_all_merged`, so fresh starts stay repeatable (`D-116`). `DebugHud::new`, `SystemTimingOverlay::default` and `InspectorState::new_with_defaults` take `ENGINE_FONT_ID`; their `font_id` fields stay public, so a game can still choose. In `tungsten-render`, `TextEngine::register` stops warning when the other face of that family, weight and style has byte-identical data; other bytes still warn (Q9). `TextEngine::load_font` on an ID that is already registered drops that ID's earlier faces once the new data has registered, as `reload_font` does, so a manifest face named `engine_mono` replaces the embedded face even with the same family, weight and style (A28, Q7); data with no face leaves the old registration in place. Text picks a face by family, weight and style, and fontdb returns the first of equal candidates (`D-116`), so like any two same-style faces under different IDs (Q9), the override is ambiguous beside another manifest face of that family, weight and style with other bytes, such as the root `mono` once a game overrides `engine_mono`: the earlier face draws, and the clash warning names both. The seam is unchanged: core gains nothing, and render learns no engine font. The examples keep their manifest `mono` for their own text until W12b.

**The action map path (step 3).** `process_hot_reload` reloads the action map only when the changed path equals the canonical `input_map_path`, through a helper beside `is_reload_root` (Q11).

**The template (step 4).** A workspace member that runs from its own folder:

```text
templates/basic/
  Cargo.toml             package tungsten-template-basic, edition 2024, rust-version as the root's, publish = false;
                         tungsten (and, for tests, its `testing` feature) as path dependencies on ../../crates/tungsten,
                         anyhow, log; no [lints], no [profile] (Q13)
  rust-toolchain.toml    byte-equal to the root's (checked by repo-check)
  tungsten.json          game.id "tungsten-template-basic", window
  input.json             move_left/right/up/down on arrows and WASD; the engine's actions by default
  assets/manifest.json   sprites: player; fonts: sans (Inter Regular); font_families: sans = [sans];
                         font_fallback ["sans"] (a fallback names a declared family, D-115); no mono
  assets/sprites/player.png
  assets/fonts/Inter/Inter-Regular.ttf, LICENSE.txt
  src/main.rs            Config::load, App::new, its manifest root, hot reload in debug builds, game::register, run
  src/game.rs            resources, systems registered by hand in order (until W15a), the text extract, the HUD on in debug builds
  src/states.rs          title -> gameplay -> pause on the state stack (D-046)
  src/components.rs      game components
  tests/game.rs          harness tests per system; the data files load
  README.md              run, test, hot reload; the guide (step 6)
  AGENTS.md              the game repository's rules that exist now (below)
  CLAUDE.md              @AGENTS.md
```

The setup that `main.rs`'s startup hook runs is a plain function the tests call, since the harness runs no startup hook. `AGENTS.md` holds: the public API only (`tungsten::…`); registry IDs, never file paths (`D-009`); actions, never keys; systems registered in `game.rs` in order; a harness test per system; `cargo test` and `cargo clippy --all-targets -- -D warnings` before a commit; where the engine's documentation lives (rustdoc through `cargo doc -p tungsten --open`, and the guide at the engine tag the game depends on). It never links into the engine's tree, which a copy lacks. The template stays under 400 lines of Rust.

**The outside-copy check (step 5).** `scripts/template-check.sh`, run by `just template-check`: it checks free space on the target folder's filesystem (floor 3 GiB, `TUNGSTEN_TEMPLATE_MIN_FREE_GB` overrides), copies `templates/basic` into a fresh `mktemp -d`, fails if a `tungsten.json`, `input.json` or `assets/` sits in any folder above the copy, rewrites each `../../crates/` path to this checkout's absolute path and fails if any relative path remains, appends the workspace's `[profile.*]` tables, copies `Cargo.lock`, then builds, tests and smoke-runs (`TUNGSTEN_SMOKE_FRAMES=3`, with a timeout) from the copy with `CARGO_TARGET_DIR=<repo>/target`, `--offline` and `--config <repo>/.cargo/config.toml`, so most artifacts are shared. A trap removes the copy.

**The guide (step 6).** `docs/getting-started.md`: install Rust (the template pins it) and GPU drivers; copy `templates/basic` out of a checkout at a release tag; replace the path dependencies with `tungsten = { git = "https://github.com/JosephGibson/Tungsten", tag = "<tag>" }`; rename the package and `game.id`; add the dev profile shown (deps at opt-level 2); `cargo run`, `cargo test`, edit an asset with hot reload; where to read next. Packaging joins with W14b.
