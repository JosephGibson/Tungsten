## 2. Design

The spike's module under the decided names (`D-130`); the level C review after step 1 covers this section and the template diff.

**Queries** (`tungsten_core::ecs::query`, public; `With` and `Without` re-exported at the crate root and at `tungsten::{With, Without}`):

```rust
pub trait QueryItem<'w>: sealed            // &A, &mut A, Option<&A>, Option<&mut A>, Entity
pub trait ReadOnlyItem<'w>: QueryItem<'w>  // the three that only read
pub trait QueryData<'w>: sealed            // one item, or a tuple of 1..=8 items
pub trait ReadOnlyQueryData<'w>: QueryData<'w>
pub trait QueryFilter: sealed              // With<T>, Without<T>, (), tuples of 1..=4
pub struct With<T>; pub struct Without<T>;

impl World {
    pub fn query<'w, Q: ReadOnlyQueryData<'w>>(&'w self) -> impl Iterator<Item = Q>;
    pub fn query_filtered<'w, Q: ReadOnlyQueryData<'w>, F: QueryFilter>(&'w self) -> impl Iterator<Item = Q>;
    pub fn query_mut<'w, Q: QueryData<'w>>(&'w mut self) -> impl Iterator<Item = Q>;
    pub fn query_mut_filtered<'w, Q: QueryData<'w>, F: QueryFilter>(&'w mut self) -> impl Iterator<Item = Q>;
    pub fn query_slices<'w, Q: ReadOnlyQueryData<'w>>(&'w self) -> impl Iterator<Item = (usize, Q::Slices)>;
    pub fn query_slices_filtered<..>, query_mut_slices<..>, query_mut_slices_filtered<..>;
}
```

Rows come in archetype order then row order, as today, so a read query and a mutable query over the same archetype set still zip by row within a frame (the physics write-back relies on it, A5). `query_mut*` runs `check_access` once and panics with the query's type name when two items name one component (`(&mut A, &mut A)`, `(&A, &mut A)`, `(&A, Option<&mut A>)`); `(&A, &A)` is allowed read-only. The public helper types the traits name (`Columns`, `ColumnsMut`, `Slot`, `SlotMut`, `OptionalRows`, the `RowsN` adapters) have private fields and rustdoc; sealed traits mean nothing outside the crate implements them.

**Migration shapes**, body-preserving, with `Entity` first where the old item had it:

| Today | On the tuple API |
| --- | --- |
| `query::<T>()` | `query::<(Entity, &T)>()` |
| `query_mut::<T>()` | `query_mut::<(Entity, &mut T)>()` |
| `query_entities::<T>()` | `query_filtered::<Entity, With<T>>().collect()` |
| `query2::<A, B>()`, `query3::<A, B, C>()` | `query::<(Entity, &A, &B)>()`, `query::<(Entity, &A, &B, &C)>()` |
| `query2_mut`, `query3_mut` | `query_mut::<(Entity, &mut A, &mut B[, &mut C])>()` |
| `query2_opt2::<A, B, C, D>()`, `query3_opt2` | `query::<(Entity, &A, &B, Option<&C>, Option<&D>)>()` and the three-column form |
| `query2_opt2_mut::<A, B, C, D>()` | `query_mut::<(Entity, &A, &mut B, Option<&C>, Option<&mut D>)>()` |
| `query3_mut_without::<A, B, C, X>()` | `query_mut_filtered::<(Entity, &mut A, &mut B, &mut C), Without<X>>()` |
| `query2_entities`, `query3_entities` | `query_filtered::<Entity, (With<A>, With<B>[, With<C>])>().collect()` |

The `ecs` and `churn` benchmark systems take the spike's tightened shapes (A7), which keep the workload and its digests. Elsewhere a shape is tightened only where a body ignores the entity in an engine crate (Q6).

**Bundles** (`tungsten_core::ecs::bundle`, public; `Bundle` re-exported at the root and at `tungsten::Bundle`):

```rust
pub trait Bundle: 'static {
    fn put<S: BundleSink>(self, sink: &mut S);   // each component value, in insertion order: sink.put(value)
    fn with<B: Bundle>(self, other: B) -> Chain<Self, B> where Self: Sized;  // provided
}
pub trait BundleSink: sealed { fn put<T: 'static>(&mut self, value: T); }   // two engine sinks: the World's staging queues, a CommandBuffer
pub struct Chain<A: Bundle, B: Bundle>(A, B);    // implements Bundle: A's components then B's
impl<A: 'static, ..> Bundle for (A, ..)          // tuples of 1..=16 components; an element is a component, never a bundle

impl World {
    pub fn spawn_with<B: Bundle>(&mut self, bundle: B) -> Entity;            // spawn, then one move into the bundle's archetype
    pub fn insert_bundle<B: Bundle>(&mut self, entity: Entity, bundle: B);   // one move; a type the entity has is overwritten
}
impl CommandBuffer {
    pub fn spawn_with<B: Bundle>(&mut self, bundle: B) -> PendingEntity;     // a Spawn and one Insert per component: the flush applies them as one move (D-084)
    pub fn insert_bundle<B: Bundle>(&mut self, entity: Entity, bundle: B);
    pub fn insert_bundle_pending<B: Bundle>(&mut self, pending: PendingEntity, bundle: B);
}
```

A bundle has one method, so there is no description to disagree with its values. The direct forms stage the values through the machinery the command-buffer flush already uses (`D-084`): `World` keeps one reusable `InsertQueues` and a `Vec<u32>` of queue indices as scratch (grown once, then no allocation), the sink's `put::<T>` pushes into the typed queue and records its index, and `Archetypes::insert_run` applies the run as one move (`storage.rs:182`), overwriting a type the entity already has or that the bundle names twice with the later value, as a run of inserts does. `spawn_with` is `spawn` then that run from the empty archetype; `insert_bundle` is the run on a live entity. The World is untouched until `insert_run` runs, so a panic inside a game's `put` leaves it consistent, and the scratch is cleared at the start of each call (`InsertQueues` gains `clear`). The buffered forms push straight into the buffer's own queues as `insert`/`insert_pending` do. The cost of the staging is a queue push and a downcast per component on the direct path, a few nanoseconds that no tracked row times (Q11); `churn`'s deferred mode is this path already. Tuple elements are components, so `(RigidBodyBundle, Transform)` would insert the bundle struct as a component; `RigidBodyBundle::dynamic(..).with((Player, Transform))` is the composition, and the rustdoc says so.

**`RigidBodyBundle`** (`tungsten_core::physics`, re-exported at `tungsten::physics`):

```rust
pub struct RigidBodyBundle { pub position: Position, pub velocity: Option<Velocity>, pub collider: Collider, pub body: RigidBody }
impl RigidBodyBundle {
    pub fn dynamic(position: Position, collider: Collider) -> Self;  // Velocity(Vec2::ZERO), RigidBody::dynamic()
    pub fn r#static(position: Position, collider: Collider) -> Self; // no Velocity, RigidBody::r#static()
    pub fn with_velocity(self, velocity: Velocity) -> Self;
    pub fn with_body(self, body: RigidBody) -> Self;
}
impl Bundle for RigidBodyBundle  // Position, Velocity when Some, Collider, RigidBody, in that order
```

A static body keeps today's three components and a dynamic one its four, so each body's final archetype is the one it has today (A5). The intermediate archetypes a spawn creates on its way follow the bundle's order, which may differ from today's insert order, and archetype IDs follow creation order (`storage.rs:41`), so step 3 checks the body iteration order directly rather than inferring it. W3b adds `PrevPosition` (`D-129`).

**Resources:** `World::resource::<T>() -> &T` and `resource_mut::<T>() -> &mut T`, which panic with ``resource `<type name>` is not in the World``; `get_resource` and `get_resource_mut` stay.

**Deprecations:** the eleven functions other than `query` and `query_mut` take `#[deprecated(since = "0.54.0", note = "...")]`, each note giving its tuple form from the table; their world tests stay under `#[allow(deprecated)]` as the shims' own tests. `query::<T>()` and `query_mut::<T>()` take query data, the ledger's two rows: a component type no longer compiles, which is the loud break `D-130` chose.

**Template diff** (reviewed after step 1): `game.rs`'s `player_movement` reads `world.resource::<Time>().delta()` and writes `for transform in world.query_mut_filtered::<&mut Transform, With<Player>>()`; `states.rs`'s `spawn_player` is one `world.spawn_with((Player, transform, sprite, Visibility::default(), SceneEntity { state_id: GAMEPLAY }))`; `tests/game.rs` reads the player with `query_filtered::<&Transform, With<Player>>().next()`.
