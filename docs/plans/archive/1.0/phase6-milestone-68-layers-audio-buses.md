## 2. Design

### 2.1 Layers and masks (W6b)

`RigidBody` gains two public fields, `layers: u32` (the layers the body is in, one bit per layer, 0 to 31) and `mask: u32` (the layers it meets), with `RigidBody::DEFAULT_LAYERS` (`1`, layer 0) and `RigidBody::ALL_LAYERS` (`u32::MAX`) as associated constants. Every constructor sets `layers: DEFAULT_LAYERS, mask: ALL_LAYERS`; `with_layers(u32)` and `with_mask(u32)` set them, as do `RigidBodyBundle::with_layers` and `with_mask`; `RigidBody::meets(&self, &RigidBody) -> bool` states the contact rule. A collider without a `RigidBody` takes the defaults. The fields go on the body component, as the card says, rather than a new component (§4 Q1).

- **Contacts.** Two bodies touch only when each one's mask holds a layer the other is in: `a.layers & b.mask != 0 && b.layers & a.mask != 0`. A pair that does not meet is never admitted (build and repair), and the safety-net sweep and the arrival pass skip it, so it makes no contact, event, island, wake or clamp. `D-064`'s and `D-092`'s passes keep their rules over the pairs that meet.
- **Tiles** are in layer 0 and meet every layer. Layer 0 is the world: a body whose mask lacks it passes tiles and every body left at the defaults.
- **Sensors** report a body or a tile in a layer their own mask holds (`sensor.mask & other.layers != 0`); the other's mask plays no part, since a sensor pushes nothing. Sensors still never detect sensors. A sensor's own `layers` matter only to queries.
- **Queries.** `SpatialFilter::with_mask(u32)` keeps the bodies, sensors and tiles in a layer the mask holds; the default is every layer, so today's filters see what they saw. Sensors still need `with_sensors(true)`.
- **Changes.** A sleeping body whose `layers` or `mask` changes wakes its island at the next step, as a `Position` write does; a static whose `layers` or `mask` changes counts as a changed support (`D-156`), so the sleepers near it wake. Both compare the values recorded at sleep and support time.
- **The fast path.** The gather writes each proxy's `(layers, mask)` into an array beside the proxies (`D-080`'s `pair_flags` pattern; `Proxy` stays 80 bytes) and sets `layered` when any proxy or sensor differs from the defaults. The pair, sweep and arrival checks read `layered` first, so a world with no layered body runs today's loops. Sensor and query checks always run; each is one AND per candidate.
- **Data.** `rigid_body` takes `layers` and `mask`, lists of layer numbers: `{ "kind": "sensor", "shape": …, "layers": [3], "mask": [2] }`. A missing `layers` is `[0]`, a missing `mask` every layer, an empty list none; a number above 31 or a non-integer fails the load at its field path. Names wait for a game that asks (§4 Q4).

### 2.2 The audio vocabulary (W6c)

In `tungsten_core::audio`, re-exported at the crate root beside `AudioCommand`:

- `AudioBus`, `#[non_exhaustive]`: `Music` and `Effects` (the default); `AudioBus::ALL: &'static [AudioBus]`; `name()` gives `"music"` and `"effects"`, which the manifest and the settings file use (serde `snake_case`).
- `Voice`: one playing instance of a sound, `Copy`, `Eq`, `Hash`, opaque; an `AudioCommands` numbers its voices from 1 and never reuses one. A command naming a voice that has ended, was dropped or never started does nothing. A replaced `AudioCommands` resource numbers from 1 again and can address a voice the old one started: a recorded limit.
- `MAX_VOICES: u32 = 64`, the voices the mixer plays at once and the largest voice limit.
- `AudioCommand` turns `#[non_exhaustive]`. `Play` gains `voice` and `fade` (the seconds over which the voice rises from 0 to its volume; 0 starts it at its volume) and turns `#[non_exhaustive]` itself, so code outside core builds it through `AudioCommands` and matches it with `..`. `Stop { handle }`, `StopAll` and `SetMasterVolume(f32)` stay as they are. New, each `#[non_exhaustive]`: `StopVoice { voice, fade }`, `SetVoiceVolume { voice, volume, fade }`, `SetBusVolume { bus, volume }`, with `fade` in seconds.
- `AudioCommands`: `play`, `play_looping` and `play_with` return the `Voice` they start (no `#[must_use]`: fire and forget stays the common call), with no fade. New: `play_faded(handle, volume, looping, seconds) -> Voice`, one `Play` carrying the fade, so a fade-in is never split from its start; `stop_voice(voice, seconds)`; `set_voice_volume(voice, volume, seconds)`; `set_bus_volume(bus, volume)`. Volumes keep today's rule (not finite or negative is 0); a bus volume is also capped at 1; seconds not finite or negative are 0.

A crossfade into the boss's music, the rustdoc example on `play_faded`:

```rust
audio.stop_voice(battle, 2.0);
let boss = audio.play_faded(boss_theme, 0.8, true, 2.0);
```

A bus's volume is the player's: a game mixes with voice volumes and fades, and `apply_settings` sets every bus from the settings.

### 2.3 Data and settings (W6c)

- **Manifest.** A sound entry takes `bus` (`"music"` or `"effects"`, default effects) and `max_voices` (1 to 64, default 64, so only the pool bounds a sound that names none); an unknown bus or a limit outside the range fails the load with the sound's ID. `SoundEntry` and `ResolvedSound` gain both fields and turn `#[non_exhaustive]` (nothing outside core builds them, A13).
- **Registry.** `SoundRegistry` keeps a bus and a limit per sound beside the volume and the loop flag: `set_bus`, `get_bus`, `set_max_voices` (clamped to 1..=64), `get_max_voices`, in the type's `get_` naming; a sound registered in code is on effects with 64. `load_sounds` sets both from the manifest.
- **Settings.** `Settings::bus_volume(AudioBus) -> Option<f32>` and `set_bus_volume(AudioBus, Option<f32>)` (clamped to 0..=1, a value that is not finite ignored). The file adds `"bus_volumes": { "music": 0.5 }`, holding only set buses; an unknown bus name is ignored whatever its value, so an older build reads a newer file, and a known one outside 0..=1 or not a number makes the file invalid, as `master_volume` does. `apply_settings` sends every bus's volume, a set one or 1.0; `App::with_plugins` queues the set ones at startup beside the master volume.

### 2.4 The mixer (W6c)

The callback owns a `Mixer` built on the main thread at init: the per-sound table (PCM, bus, limit) indexed by handle, 64 voice slots, the two buses and the master gain. Nothing in the callback allocates: `Play` takes a free slot and never grows a vector.

- **Gain.** A voice plays at its volume × its bus's volume × the master volume. A `Play` with a fade starts at 0 and rises to its volume over the fade. Volume changes ramp linearly per frame: a voice's over its command's `fade`, at least 10 ms; the master's and a bus's over 10 ms, so a slider's step does not click. A stopping voice ramps to 0 over its fade, at least 10 ms, then ends and frees its slot; later commands to it do nothing. `Stop` and `StopAll` stop with the 10 ms ramp.
- **Limits.** A voice fading out after a stop counts toward no limit. A `Play` of a sound whose playing voices fill its limit ends the sound's oldest one-shot voice, or its oldest loop when no one-shot of it is playing, at once, and takes that slot: a burst replaces its own hits before the loops a game keeps. Under its limit, a `Play` takes a free slot; with all 64 slots busy, the slot of a voice fading out after a stop, else of the oldest one-shot of any sound; when all 64 slots hold playing loops, the `Play` is dropped. A voice the limit ends is cut, not faded. A sound with no samples plays nothing.
- **What the stage can know.** A one-shot's natural end happens in the callback, but under these rules no one-shot's end decides a loop's fate: a loop ends only by a stop command, or by a `Play` of its sound while the sound's loops alone fill its limit, and a loop's `Play` is dropped only while 64 loops play. The stage sees every command, so it knows exactly which loops play (§2.6).
- **Output.** The mix is clamped to [-1, 1] (the owner's call in known issues; §4 Q9). Stereo PCM goes to the first two channels of a wider device, the rest silent; a mono device takes the mean of left and right.

### 2.5 The ring policy (W6c; `D-034`)

- The ring holds 1,024 commands, allocated once at init.
- Before sending, the audio stage keeps at most a sound's `max_voices` `Play` commands of that sound per frame, the last ones; the earlier voices never start. The harness's capture list takes the same commands, so tests see the cap.
- Commands that do not fit the ring wait, in order, and go before newer ones. `AudioSystem::flush`, public and non-blocking, moves waiting commands into the ring as far as it has room; `send` flushes before it queues, and the audio stage calls `flush` every frame, with new commands or none, so a waiting command moves as soon as the callback frees room.
- While 4,096 or more commands wait, a new one-shot `Play` is dropped and counted (a burst whose hits would come late); every other command, a loop's `Play`, a stop or a volume, still waits, so no state is lost.
- The outbox keeps a latch of the state it admits (§2.6's rules): the master volume, each bus's volume and the loops playing. Past 65,536 waiting commands, a callback stalled or swamped, it resynchronizes instead of dropping state: it clears the queue and queues `StopAll`, then the latch's master and bus volumes and its loops from their start under their own voices, so the mixer comes back to the latch's state once it drains them; the one-shots that waited are counted as dropped. The stage logs each count at most once a second.
- The callback takes at most 1,024 commands, one ring's worth, before it renders its buffer; the rest stay in the ring for the next callback, so a producer that keeps refilling the ring cannot hold the output back.

### 2.6 The latch and the lost device (W6c)

**The latch** (step 3) applies §2.4's rules to the commands the outbox admits, in order, after the cap and the one-shot bound: a stop or `StopAll` removes loops, a `Play` of a sound whose latched loops fill its limit removes the oldest, a loop's `Play` with 64 loops latched is dropped, a one-shot is never latched, and the master, bus and voice volumes keep their last values. Every admitted command reaches the mixer or is replaced by a resync from the latch (§2.5), so the latch's loops are the mixer's playing loops. It replays as commands: the master volume, each bus's volume and every loop, at its last volume and from its start, under its own `Voice`.

**The lost device** (step 4). The error callback only sets flags: `DeviceNotAvailable` and `StreamInvalidated` mark the stream lost, and any other kind (an ALSA xrun among them) adds to a counter that the audio stage logs at most once a second. When the stream is lost, the stage logs once, clears the waiting queue (the latch already holds what waited, and its one-shots are stale), drops the old stream (one callback thread at a time, `AGENTS.md`), opens the default device again with `AudioSystem::init` and replays the latch into the new ring. While the stream is lost, commands update the latch and nothing waits. A failed rebuild retries every two seconds.

### 2.7 The listening host (example 05)

The card's owner-only check is listening to the buses and a crossfade, so the UI lab, the reference for a game's UI and its settings screen, carries it. The root manifest puts `music_main` on music and `sfx_blip` on effects. The play state starts `music_main` faded in over one second on entry and fades it out over half a second on exit; music keeps playing through pause and the inventory, as the game's spec has it. The settings screen gains "Music" and "Effects" sliders (0 to 100 by 5) under "Volume", applied live and saved by Back like the others; each Effects change plays `sfx_blip`. In play, `audio_toggle_music` (M in the root `input.json`, the key example 01 uses for its music) crossfades the music into a new voice from its start over two seconds. No file is added: the code goes in `menus.rs` and `main.rs`.

### 2.8 The seam

Core keeps no `cpal` or `rtrb` type (`D-007`, `D-018`): buses, voices, commands, the registry's defaults and the settings are core's; the ring, the mixer, the limits' cap, the latch and the rebuild are the umbrella's. No new dependency, thread, system or stage; `DefaultPlugins`' schedule is unchanged. The public `tungsten::audio::AudioSystem` keeps `init` and `send`, whose doc changes from "drops when full" to the waiting rule, and gains `flush` (§2.5).
