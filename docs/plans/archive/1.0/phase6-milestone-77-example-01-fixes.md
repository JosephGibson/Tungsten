## 2. Design

### 2.1 Item 1: tile proxies cached across steps

The rule `D-080` set for the broadphase holds for every part: no query result, candidate order or digest changes.

- **The cache.** `PhysicsBuffers` keeps the tile proxies (face masks, keys, sensor identities) with the maps they came from: each map's entity, origin bits, tile and map sizes, and every collision layer's index among all the map's layers (a tile's identity holds it, `step/gather.rs:30-37`) with its tiles. Each step checks the maps in query order against it (the tile slices compared with `==`, about 31,000 `i32` a layer); any difference, or a map added, gone or reordered, rebuilds it with today's scan and bumps its version. The gather appends the cached tail after the entity proxies, so proxy order, keys and identities are today's.
- **The pair grid.** Entity proxies stage into the grid per build as now; the tiles stage once per cache version, cell size and inflation (`2·linear_slop`, `step/pairs.rs:186`) into a grid of their own, their inflated boxes kept for the pair arrays, ordinals offset by the entity count at query time. One walk visits both, cell by cell, a cell's entity entries before its tiles, which is the order one grid holding both returns (staging order within a cell, `broadphase.rs:1-10`). Every pair-grid query uses it: the build, a repair, the arrival pass and the sweep (whose statics-only grid stages the entity statics and walks the same tile grid).
- **The passes.** The substep's passes whose bodies skip tiles run over the entity prefix (A5).
- **The index.** Its tile entries and their exact-box grid are kept per cache version; bodies and sensors are rebuilt each step; ids stay proxies, then tiles, then sensors. Queries take the union of both grids' candidates: ties already go by id (A6).
- **The sensor pass.** A sensor whose centre, shape and mask match the last step's, with the cache unchanged, reuses its sorted tile pairs, none of which can be new, and tests only bodies; any other sensor runs today's test over tiles too. The step's pairs merge sorted, so the list and the events (bodies in index order, then tiles) are today's.
- **Proof.** The core physics tests (90 step tests with the D-063 reference model), `just physics-release`'s pinned hashes, the bench rows' digests, 01's tests, and a differential probe hashing every body's position, every `CollisionEvent` and `SensorEntered` over a scripted 01 run before and after. New tests: the cache equals a fresh scan after a map is edited, moved, added and despawned, and after a non-collision layer is inserted before its collision layer; a changed `linear_slop` restages the tile grid; the two-grid walk returns one grid's order on mixed cells.
- **If caching leaves `physics_step` above 0.6 ms at the idle spawn** (0.96 read 0.46 here): merged static boxes come next, under their own decision, since they change contacts and per-tile sensor identity. Otherwise not.

### 2.3 Item 3: the autosave

`D-160`'s why is a newer build's save; `D-181` keeps any failed slot for the run. Both hold for what they protect, and a fourth state says what an upgrader has:

- `SlotState::Older`, from `SaveError::Migration`: a save of an older schema this build cannot read. The save screen labels it "Saved by an older version". A manual slot stays read-only as today.
- An autosave takes, in order: an empty slot (by number), an `Older` one (oldest header time, then number), the oldest `Ready` one (as today), and a `Damaged` one (lowest number) only when no other autosave slot can be written. `Newer` is never written. The rotation reads the three autosaves alone.
- Tests in the template: three refused older autosaves take the next three autosaves, then rotate; a newer autosave survives every autosave; three damaged ones give one written slot and keep the other two. In 01: three schema 6 autosaves get an autosave (step 3), and three schema 7 autosaves migrate and rotate after schema 8 (step 7).
