## 2. Design

### 2.1 `Time`

```rust
impl Time {
    pub fn fixed_step(&self) -> f32;                       // 1/60 s
    pub fn set_fixed_step(&mut self, secs: f32);           // panics unless finite and > 0
    pub fn max_steps_per_frame(&self) -> u32;              // 2
    pub fn set_max_steps_per_frame(&mut self, steps: u32); // panics on 0
    pub fn fixed_steps_this_frame(&self) -> u32;
    pub fn dropped_this_frame(&self) -> f32;               // whole steps, game seconds
    pub fn alpha(&self) -> f32;                            // [0, 1)
    pub fn interpolate(&self) -> bool;                     // true
    pub fn set_interpolate(&mut self, on: bool);
    pub fn enter_fixed_step(&mut self);                    // delta() is the step
    pub fn leave_fixed_steps(&mut self);                   // delta() is the game dt
}
```

`advance_frame` keeps W3a's clocks, then adds the game dt to an `f32` accumulator, subtracts one step at a time while it holds a whole step and fewer than the bound have run, and if a whole step is left drops `acc − acc % step` and keeps the remainder: the spike's loop, which A18 and w03's "67 ms dropped" assume. `alpha()` is the remainder over the step. The sum saturates at `f32::MAX` and the loop never runs past the bound or on a subtraction that no longer changes the sum, so every accepted input leaves a finite accumulator, `alpha` in [0, 1) and at most the bound's steps. The setters take effect at the next `advance_frame`. `delta()` is the step between `enter_fixed_step` and `leave_fixed_steps`, the game dt otherwise, so a world driven by hand that never calls them reads the game dt as today. A paused frame adds nothing: no step, `alpha` held. `fixed_step()` of a new `Time` equals `1.0_f32 / 60.0`, the smoke pin and the harness default. A step longer than `PhysicsConfig::max_step_dt` makes physics run slow against the game (`D-094`); the setter's rustdoc says so and the config refuses one (§2.5).

### 2.2 Input and events

- `InputState::set_fixed_view(on)` and `end_fixed_step()`. Each press and release enters the frame view and a fixed view; while the fixed view is on, `just_pressed`, `just_released`, `mouse_just_*` and `scroll_just_*` answer from it; `end_fixed_step` clears it after each step, and `begin_frame` clears the frame view only (scroll releases enter both). A frame with no step keeps its edges for the next step; a frame with two shows each edge to the first. Level queries, the cursor and the deltas stay per frame. `ActionMap` inherits the view.
- `World::set_fixed_event_view(on)` and `World::end_fixed_step_events()` reach every registered queue through a table beside `flush_events`' (the queue's own methods are crate-private). In the first step a queue reads as today; in a later step its readers (`iter`, `iter_current`, `len`, `is_empty`) see only the events sent since the step before it ended, so an event sent in a step reaches that step's later `iter_current` readers once, never the next step's (Q11); `iter` in a first step still includes the previous frame, as today. Outside the steps a queue reads the whole frame, all steps' events included. An event sent outside the steps reaches a fixed-stage reader only in a step that runs after it in the same frame (`iter_current`) or in the next frame's first step (`iter`); when neither comes, it rotates out unseen, which is common at 144 Hz (Q12).

### 2.3 The frame

```text
time          advance_frame: clocks, accumulator → steps, dropped, alpha; DeltaTime.dt = game dt
pre_update    game dt, frame views
fixed_update  × steps: Time::enter_fixed_step, DeltaTime.dt = step, fixed input and event views;
              physics_prev_snapshot, [opt-in gameplay], physics_step; then end_fixed_step (input, events)
              after the last: Time::leave_fixed_steps, DeltaTime.dt = game dt, frame views
update        game dt, frame views, exit check
post_update   physics_sync, then the engine's chain as today
flush, extract, render, audio, InputState::begin_frame, telemetry
```

A world without `Time` runs `fixed_update` once with no swap, as today; one without `InputState` skips its calls.

### 2.4 Interpolation

- `PrevPosition(pub Vec2)` beside `Position`. `RigidBodyBundle::put` gives `Position`, `PrevPosition` (the same point), `Velocity` when `Some`, `Collider`, `RigidBody`: four components static, five dynamic, no new field (Q3).
- `physics_prev_snapshot` copies `Position` into `PrevPosition` for every entity with both. `physics_sync` writes `Transform.position = prev + (cur − prev) × alpha` where `PrevPosition` is present and `Time::interpolate()` is on, `Position` otherwise and in a world without `Time`. Both take the slice forms with `for_each` at both levels (`D-135`'s rule for hot reads; the optional column is per archetype). `Position` is never written (`D-033`).
- `PhysicsPlugin` registers `physics_prev_snapshot` in `FixedUpdate`, `physics_step` `.after(PHYSICS_PREV_SNAPSHOT)`, and `physics_sync` under `PHYSICS_SYNC` in place of `sync_position_to_transform` (Q5). The sort takes the earliest-registered ready system (`schedule.rs:365-370`), and `DefaultPlugins` builds before a game's plugins, so the snapshot runs first and a step's history spans opt-in gameplay's moves and the solve (Q6).
- A teleport writes `Position` and `PrevPosition` together. The physics overlay keeps drawing `Position` (`D-042`), leading an interpolated sprite by up to one step; `DESIGN.md` says so. A game whose own extract draws from `Position` interpolates there, as example 01 does (§2.7).

### 2.5 The `time` section

```json
"time": { "fixed_step_hz": 60, "max_steps_per_frame": 2, "interpolate": true }
```

`TimeConfig` (`#[non_exhaustive]`, every field defaulted) is `Config.time`. `fixed_step_hz` is a `u32`, so 60 gives the pin exactly. `TimeConfig::validate` returns `ConfigError::InvalidValue` for `fixed_step_hz` below 30 (a step past `max_step_dt`'s default 1/30 s) and `max_steps_per_frame` of 0 (Q4); `Config::load` and `App::new` call it, as they call `GameConfig::validate`, and `App::new` applies the section to `Time`. No checked-in `tungsten.json` gains the section.

### 2.6 Telemetry

`FrameTimings::fixed_steps: u32`. The fixed loop times every run; the k-th system of each later step adds to the k-th entry the first step pushed, so a name appears once a frame in stage order. A frame with no step lists each `fixed_update` system at 0 ms (Q2), from `Schedule::names(Stage::FixedUpdate)`. The `frame:` line is unchanged.
