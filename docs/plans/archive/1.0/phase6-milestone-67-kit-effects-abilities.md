## 2. Design

The API sketch; the step 1 critique reads step 1's diff against it. Every value type keeps private fields behind a constructor and `with_*` builders; data derives serde; every public item has rustdoc with a doctest. Phase edges: `effect_tick` and `ailment_tick` after `stats_apply` (so an expiry never takes a modifier before the consumers read it, and the drain reads the `Health::max` the stat wrote); `ability_tick` after `action_input` and `aim`; `ailment_feed` after `damage_resolve`; `effect_resolve` after `damage_resolve` and `ailment_feed`; `level_tick` before `cues`; each `if_present`.

### 2.1 Curves (`foundation/curve.rs`)

`Curve`: points `(x, y)` with `x` strictly increasing, at least one, all finite; `Curve::new(points)`, `at(x) -> f32` linear between points and held at the ends; `points()`. Data form `[[1, 0], [2, 10], [3, 25]]`, the `curves` kind's entry and a `DataRef<Curve>` in place; shape `curve`. `register_curves(world)` (crate-private) registers the kind and its description once, from whichever of `EffectsPlugin` and `LevelPlugin` builds first. A curve that scales an effect (§2.2) has every `y` at least 0, checked at the load of the effect that names it (a negative `y` fails the load naming the field), and what it scales runs in `f64` and clamps to `f32::MAX`, so a factor never makes a part negative or a modifier infinite (`DamagePart::new` and `Stats::add_modifier` refuse those).

### 2.2 Effects (`damage/effects.rs`)

**`Effect`**, a definition, the `effects` kind's entry or inline:

```jsonc
{ "duration": 3,                       // seconds; absent: infinite; 0: instant (Q1)
  "period": 0.5,                        // > 0: the payload lands at the end of each period; absent: once at application
  "damage": { "elemental.fire": 1 },    // the payload's hit, periodic, from the instance's source; a number or a map (FieldType::Damage); 0 by default
  "heal": 0,
  "stack": { "limit": 3, "refresh": "extend", "expire": "remove_one" },   // limit 1, refresh "refresh", expire "clear" by default
  "modifiers": [{ "stat": "move_speed", "modifier": { "pct": -0.2 } }],   // per stack, on the target's Stats; the shape `stat_modifier`, `modifier` one-of add|pct|mul|override
  "resist": [{ "tag": "digital", "modifier": { "add": 0.25 } }],          // per stack, on the target's Resist (Wither, corrosion); shape `resist_modifier`
  "grant": ["status.burning"], "blocked_by": ["status.wet"],              // declared tags
  "scale": { "curve": "burn_scale", "into": ["duration", "periodic", "modifiers"] },   // optional; `into` all three by default
  "on_expire": "thawed" }                                                 // optional; applied to the target from the same source at a timed end
```

Rust: `Effect::new()`, `with_duration`, `with_period`, `with_damage(parts)`, `with_heal`, `with_stack(limit, Refresh, Expire)`, `with_modifier(stat, Modifier)`, `with_resist(tag, Modifier)`, `with_grant(tags)`, `with_blocked_by(tags)`, `with_scale(DataRef<Curve>, Into)`, `with_on_expire(DataRef<Effect>)`; getters. `Refresh { Refresh, Keep, Extend }`, `Expire { Clear, RemoveOne }`, `#[non_exhaustive]`.

**`Effects`**, the component, scene name `effects`: a list of `DataRef<Effect>` applied at the entity's first `effect_tick` with no source (`["regen", { "duration": 2, ... }]`), and the active instances. `Effects::new()`, `with(DataRef<Effect>)`, `instances() -> impl Iterator<Item = &EffectInstance>`, `has(id) -> bool`, `stacks(id) -> u32`. `EffectInstance`: `effect() -> &DataRef<Effect>`, `source() -> Option<Entity>`, `stacks()`, `left() -> Option<f32>`, `serial() -> u64`. The save holds the active list (`effect`, `stacks`, `left`, `period_left`, `factor`, `serial`, `granted`), `next_serial` and the granted-tag table (`tag`, `owners`, `prior`); a source is an entity and not saved (Q9). `effect_resolve` inserts an `Effects` on a target that lacks one.

**`EffectRequest`**: `new(target, DataRef<Effect>)`, `with_source(Entity)`, `with_scale(f32)` (1 by default), `apply(world) -> Applied`, `queue(world) -> bool`; `Applied { Applied, Stacked, Blocked, Ignored }`, `#[non_exhaustive]`. `end_effect(world, entity, &DataRef<Effect>) -> bool` removes an instance early.

**The resolution** (`effect_resolve`, `kit_resolve`, after `damage_resolve` and `ailment_feed`): first the step's `on_expire` requests in the order `effect_tick` queued them (entity order), then the other queued requests sorted by target, then source, none first, so an expiry's transition lands before any new application on the same step (a thaw grants `status.thawed` before a second source's cold hit asks to freeze, Q18); every kit path goes through here, a fresh `Effects`' pending list, the `on_expire`s, the cues, the ladder, the abilities and the offers, which queue, so no kit payload lands in `kit_tick` and a lethal one starts its death delay in `kit_resolve` whatever the plugins' registration order (`health_tick` counts it from the next step). `EffectRequest::apply` is a game's immediate exception, as `DamageRequest::apply` is for damage (Q19): the same resolution at once, its outcome returned, its timing the caller's. A target gone, despawning or dead is `Ignored`. A target carrying any `blocked_by` tag is `Blocked`, traced. The factor is `scale.curve.at(request.scale)` when the effect has a `scale`, else 1. No instance of the effect (`DataRef` equality): one is made with the next serial, stacks 1, `left = duration × factor` (`None` for infinite; `duration` scales only when `into` names it), `period_left = period`; its modifiers go on the target's `Stats` and `Resist` under the source `effect#<serial>`, `add` and `pct` values times the factor when `into` names `modifiers`, `mul` and `override` as written (A6), each product in `f64` clamped to `±f32::MAX`; its `grant` tags go into the target's `Tags` (inserted if absent), onto the instance as the list it granted, and into the component's ownership table, one row per tag with the count of live instances granting it and whether the entity carried it before the first grant (Q10); an instance is governed by the definition it was applied with for what it placed (its granted list, its modifiers, its duration), while its period's payload reads the current definition at each tick, so a reload that changes a `grant` releases the old tag at expiry and a changed `damage` tunes live (Q20); the payload lands once at application when the effect has no `period`, through `DamageRequest::apply` with `with_periodic(true)` and the instance's source, or `HealRequest::apply`; `EffectApplied` goes out. An instance present: stacks below the limit take one more, at the limit keep their count; the duration follows `refresh` (restart, keep, add); the factor becomes the request's; the modifiers are rebuilt as `stacks` copies; `EffectApplied` goes out with the count. An instant effect (`duration` 0) lands its payload and queues its `on_expire` for the next step and keeps no instance: no modifiers, no tags.

**The tick** (`effect_tick`, `kit_tick`, after `stats_apply`): a modifier placed in step N's resolve reaches the movers, health and cooldowns through step N+1's `stats_apply`, and an expiry in step N+k's tick comes after that step's `stats_apply`, so an effect of k steps moves its consumer for k steps and a one-step effect for one. Per entity in order, each instance's `left` counts down by `Time::delta`; `period_left` counts down by the step's time inside the lifetime, `min(dt, left)` for a timed instance, so no elapse falls past the end (a duration of 0.01 s with a period of 0.005 s lands two ticks in a 1/60 s step, not three), each elapse queueing the payload (a `DamageRequest::from_parts` of the `damage` map's parts times the factor when `into` names `periodic`, `with_periodic(true)`, the source, no position, no knockback, no crit; a `HealRequest` for `heal`), at most 16 elapses a step as `Cooldown` bounds them, resolved by this step's `damage_resolve`. At `left` 0: `expire: clear` removes the instance (its modifiers by source; each tag on its granted list drops the table's count by one, and a tag at 0 that the entity did not carry before leaves its `Tags`, whichever instance granted it first, Q10), sends `EffectExpired` and queues `on_expire` for this step's `effect_resolve`; `remove_one` drops one stack, rebuilds the modifiers and restarts `left`, and at 0 stacks ends as `clear`. The pending list of a fresh `Effects` is queued here at its first run, one `EffectRequest` per entry with no source.

**Events**: `EffectApplied { entity, source: Option<Entity>, stacks: u32, id: Option<String> }` and `EffectExpired { entity, id: Option<String>, ended: bool }` (true for `end_effect`), `Clone`, `#[non_exhaustive]`, `id` the kind entry's ID or `None` for an inline effect (A22). Cue events `effect_applied` (the subject, its other the source, its amount the stacks) and `effect_expired` (the subject). The trace records `effect_applied`, `effect_expired`, and `Skipped { event: "effect", action: "apply", why }` for a blocked or ignored request.

**The `effect` cue action**: `{ "effect": "burning" }` or `{ "effect": { "id": "burning", "target": "other" } }`, the definition in place allowed; `target` `self` by default. The request's source is the occurrence's other entity when the effect lands on the subject and the subject when it lands on the other; a missing other skips with `NO_OTHER`. It queues, so it applies the next step's `effect_resolve`. `CueAction::effect(DataRef<Effect>)`, `for_other`.

**The periodic flag** (`damage/pipeline.rs`, `damage/health.rs`): `DamageRequest::with_periodic(bool)`, `is_periodic()`; a periodic request passes the window guard (`takes_hits` reads the flag) and `Health::hurt` starts none for it; it starts no flash and carries no knockback or crit (Q3). `Damaged.periodic` and `DamagedPart.periodic`, `with_periodic`, false from `new` (A3). The resolve order, events and trace are M66's otherwise.

### 2.3 Abilities (`intent/ability.rs`)

**`Ability`**, a definition, the `abilities` kind's entry or inline:

```jsonc
{ "trigger": { "action": "attack" },                 // one of { "action": slot }, { "interval": seconds > 0 }, { "manual": {} } (default)
  "cost": { "stat": "mana", "amount": 10 },          // optional: spends the stat's base; a base below it refuses the use
  "cooldown": 0.8,                                    // seconds >= 0, counted at the `cooldown_rate` stat's rate (A11)
  "charges": { "max": 6, "refill": 1.5, "all": false },   // optional: a charge per use; one back every `refill` seconds, or all of them `refill` seconds after the last runs out with `all`
  "target": { "nearest": { "all": ["team.enemy"], "range": 320 } },   // one of { "self": {} } (default), { "aim": {} }, { "nearest": filter + range }, { "random": filter + range }
  "payload": [{ "spawn": { "prefab": "bolt", "speed": 420, "offset": 12 } },   // at least one, run in order
              { "effect": "swift" }, { "impulse": 600 }, { "hitbox": 0.2 }] }
```

Rust: `Ability::new()`, `with_trigger(Trigger)`, `with_cost(stat, amount)`, `with_cooldown`, `with_charges(max, refill, all)`, `with_target(AbilityTarget)`, `with_payload(Payload)`; `Trigger { Manual, Action(String), Interval(f32) }`, `AbilityTarget { Self_, Aim, Nearest { filter, range }, Random { filter, range } }`, `Payload { Spawn { prefab, speed, offset }, Effect(DataRef<Effect>), Impulse(f32), Hitbox(f32) }`, each `#[non_exhaustive]`.

**`Abilities`**, the component, scene name `abilities`: `["wand", { inline }]`; an entry's name is its ID, or `#<index>` in the list for an inline one (Q5), and names are unique in one component: a list naming an ID twice fails the load, and `with` of an owned name replaces that entry. `Abilities::new()`, `with(DataRef<Ability>)`, `names()`, `ready(name) -> bool`, `cooldown_left(name) -> Option<f32>`, `charges(name) -> Option<u32>`, `refill(name) -> bool`. Saved with each entry's state.

**The use**: `use_ability(world, entity, name) -> Used`, `Used { Used, NotReady, NoCharge, NoCost, NoTarget, NoAbility }`, `#[non_exhaustive]`. The target first: `self` is the entity's point with the direction from its `Aim` (`direction()`), else its `Intent`'s aim, else none; `aim` needs that direction; `nearest` scans the filter's matches gathered by `motion::target`'s resolver (A13) and `random` draws one of them within range from `KitRng`, both over the eligible matches only: alive, not `Despawning`, and not dead by a `Health` (an entity without one is eligible), so a nearer corpse never outranks a living enemy and nothing is spent on a target the effect would ignore. No target, no direction for a payload that needs one (`spawn` with `speed` above 0, `impulse`), spends nothing: `NoTarget`. Then the cost (the stat's base, A6), a charge and the cooldown are spent, the payloads run in order, `AbilityUsed { entity, name: String, target: Option<Entity>, position: Vec2 }` goes out (`Clone`, `#[non_exhaustive]`) and the trace records `ability_used`. `spawn`: the prefab at the entity's point plus `offset` along the direction, `spawn_prefab_from(entity, prepared.with((LinearMotion::new(direction × speed),)))` when `speed` is above 0 (A16), as it is otherwise; the load checks the prefab ID and, with a `speed`, that the prefab has a `linear_motion` (A16). `effect`: an `EffectRequest` on the target entity (`nearest`, `random`) or the entity itself (`self`, `aim`), from the entity, queued. `impulse`: `knock_back(entity, direction × speed)` (A15; a skip is traced). `hitbox`: the entity's own `Hitbox` armed for the seconds (§2.5; absent, traced).

**The tick** (`ability_tick`, `kit_intent`, after `action_input` and `aim`): per entity in order, each entry's cooldown counts down at the entity's `cooldown_rate` (1 without it), its refill and its interval on the game clock; an `action` trigger uses when `Intent::pressed(slot)` (no `Intent`, never); an `interval` trigger uses each time its interval elapses, at most one use a step. `KitRng` draws in entity order.

**The `ability` cue action**: `{ "ability": "wand" }` or `{ "ability": { "name": "wand", "op": "refill", "target": "other" } }`, `op` `use` (default) or `refill` (every charge back), `target` `self` or `other`: trigger by event through cues (Q4), and refill by pickup through a pickup's `picked_up` cue on its collector. A use from a cue runs in `kit_react` at once. `CueAction::ability(name)`, `with_op`, `for_other`.

### 2.4 Levels (`react/level.rs`)

**`Level`**, the component, scene name `level`: `{ "counter": "xp", "target": "self", "curve": "hero_xp", "offers": "hero_offers" }`; `target` `self` (the entity's `Counters`) or `game`; `offers` optional. The curve maps a level to the total count that reaches it; its last point's `x`, floored, is the top level (Q12). `Level::new(counter, DataRef<Curve>)`, `with_game_counter`, `with_offers(DataRef<Offers>)`, `level() -> u32` (1 at the start), `offers() -> &[Offer]`, `choose(index) -> bool`. **`Offers`**, the `offers` kind's entry or inline: `{ "count": 3, "entries": [{ "weight": 2, "gives": { "effect": "swift" } }, { "weight": 1, "gives": { "ability": "wand" } }] }`; `Offer`: `effect() -> Option<&DataRef<Effect>>`, `ability() -> Option<&DataRef<Ability>>`. **`LevelUp { entity, level: u32 }`**, `Copy`, `#[non_exhaustive]`; cue event `level_up` (the subject, its amount the level).

**The tick** (`level_tick`, `kit_react`, before `cues`): per entity in order, while the level is below the top and the counter reaches `curve.at(level + 1)`, at most 16 times a step as `Cooldown` bounds its elapses (the rest carry to the next steps, so a curve of a billion levels stalls no frame): the level rises, `LevelUp` goes out, the trace records `level_up`, and `count` distinct offers are drawn by weight without replacement from `KitRng` (fewer when the entries are fewer), replacing any pending ones (Q8). A `choose` made since the last tick applies here: an effect as an `EffectRequest` on the entity, queued; an ability pushed onto the entity's `Abilities` (inserted if absent), or, when the entity owns that name already, that entry refilled and its cooldown cleared (Q17); the pending offers clear.

### 2.5 The hitbox window (`overlap/hit.rs`)

`Hitbox::with_window(seconds)`: a windowed hitbox starts disarmed and hits only while its window runs; `arm()` rearms it (every target may be hit once more) and opens the window; `is_armed()`. A hitbox without a window is always armed, as today. `hitbox_tick` skips a disarmed hitbox and counts the window down at the end of its run (Q6); a projectile runs its hitbox as before, window or not. Scene field `window` (seconds above 0, `null` by default); the save adds `window` and `armed_left`.

### 2.6 Ailments (`damage/ailments.rs`, `damage/kinds.rs`)

**`ailments`** on a `damage_types` definition: a ladder of rungs from the lowest up, `[{ "effect": "chilled", "needs": 0.5, "requires": [], "chance": 1, "window": 4 }, { "effect": "frozen", "needs": 1, "requires": ["status.chilled"], "window": 4 }]`, which the feed climbs from the top rung down (Q15); shape `ailment_rung`: `effect` a `DataRef<Effect>`, `needs` a fraction of the threshold above 0 or `null`, `requires` declared tags the target must all carry, `chance` in `(0, 1]` (1 by default), `window` seconds above 0, required with `needs`. The load checks each rung's effect, tags and numbers. An entry without `ailments` takes its nearest ancestor's ladder, as `label_style` is inherited (A4), and a part feeds the bucket named by the entry whose ladder it resolves to (Q30).

**`AilmentThreshold`**, scene name `ailment_threshold`: `{ "flat": 20, "of_max_health": 0.1 }`, both at least 0; the threshold is `(flat + of_max_health × Health::max) × ailment_threshold_mult`, the stat read when present and floored at 0, 1 without it (Q7, Q32); a threshold of 0, or no component, leaves the rungs with `needs` skipped. **`AilmentBuckets`**, a runtime component the feed inserts: fills by type name, saved as `{ "elemental.cold": 12.5 }` and shown as inspector rows.

**The feed** (`ailment_feed`, `kit_resolve`, after `damage_resolve`): reads `DamagedPart` through a cursor; a periodic part or one of no kinds feeds nothing (Q29). The part's deepest type (A4) resolves to a ladder; the bucket of that entry's name takes the amount; then the rungs from the last to the first, so the ladder climbs to the highest rung the target can reach: `needs` passes when the threshold is above 0 and the fill reaches `needs × threshold`; `requires` when the target carries every tag, the tags of the effects the feed queued for that target earlier in the same run counted as carried (a per-run pending set, cleared at the run's end), so two full buckets in one step chill then freeze as they would across two steps (Q21); `chance` draws `KitRng` only when both passed, in event order. The first rung that passes queues `EffectRequest::new(target, effect).with_source(part.source).with_scale(fill / threshold, or 1 without a threshold)` for this step's `effect_resolve`, empties the bucket and ends the walk for that part; with the ladder above, a full bucket on a target without `status.chilled` chills it, and the next full bucket, `status.chilled` granted, freezes it. **The drain** (`ailment_tick`, `kit_tick`, after `stats_apply`, so the threshold reads the `Health::max` a `max_health` stat wrote this step): each bucket loses `threshold / window` a second, the window the ladder's first `needs` rung's (Q31), and an empty bucket leaves the map.

## 4. Open questions

| # | Question | Default |
| --- | --- | --- |
| Q1 | What is an instant effect (`duration` 0)? | Its payload lands at application and its `on_expire` queues; it keeps no instance, so its modifiers and tags do nothing; `EffectApplied` and `EffectExpired` go out in that step. |
| Q2 | The `effect` action on a `hit` cue runs for a hit the target's window ignored, since `Struck` precedes the resolve (A10). Should hit items take an `apply` list that lands with the request? | No: cues and the ladder are the ways; the `apply` list is a backlog row until a recipe needs it. A recipe that must land with the hit uses a `damaged_part` rule with a `kind` filter on the victim's side. |
| Q3 | A periodic hit and the flash, knockback and crit? | No flash, no knockback, no crit: the effect's request carries none, and `resolve` skips the flash for a periodic request. |
| Q4 | Trigger by event? | The `ability` cue action, since cues are the one way to react to events in data; no `event` form on `trigger`. |
| Q5 | The name of an inline ability? | `#<index>` in its list; a cue that names one by `#0` works, and an ID reads better. |
| Q6 | Where does the hitbox window count down? | In `hitbox_tick`, after the armed check, so a window of N steps lands N steps; the one timer outside `kit_tick`, since it gates that system alone. |
| Q7 | `ailment_threshold_mult` well-known? | No (Q32): the fixtures declare it in their `stats` kind, and the feed reads it when present. |
| Q8 | A level-up while offers are pending? | Replaces them; a game that wants a queue reads `LevelUp`. |
| Q9 | An effect's source after a load? | `None`: an entity is not data; the instance keeps everything else. |
| Q10 | A granted tag the entity already carried, or another instance grants? | The component counts each granted tag's live granters and whether the entity carried it before the first grant; a tag leaves when its count reaches 0 and it was not carried before, whichever instance granted it first, and the table is saved with the instances. |
| Q11 | The template change? | The hazard's `hit` cue slows the player by one `effects` entry; the player's `stats` gains `move_speed` so the mover follows the stat. |
| Q12 | A curve outside its points? | Held at its ends; a level curve's last `x`, floored, is the top level. |
| Q13 | `KitRng`'s draw order for abilities and ailments? | Abilities in entity order within `ability_tick`, ailments in event order within `ailment_feed`, each after the step's earlier draws (cooldown jitter in `kit_tick`), so a seed repeats a run. |
| Q14 | Effects on a target without `Stats`, `Resist` or `Tags`? | Modifiers on a missing `Stats` or `Resist` do nothing (A6), traced once per instance; a missing `Tags` is inserted for `grant`. |
| Q15 | Which way does the feed walk a ladder? | From the last rung to the first, so a ladder written from the lowest up climbs to the highest rung the target can reach; the first rung that passes triggers and empties the bucket. |
| Q16 | How many level-ups a step? | At most 16 per entity, as cooldowns bound their elapses; the rest carry to the next steps. |
| Q17 | An offer that grants an ability the entity owns? | Refills it and clears its cooldown; an upgrade is an effect, composed in the offer's list. |
| Q18 | An expiry's `on_expire` beside a new application on the same step? | The `on_expire` requests resolve first, in the order the tick queued them, then the sorted rest, so a transition's grant precedes the step's new applications. |
| Q19 | `EffectRequest::apply` beside the resolve's timing guarantee? | The game's immediate exception, as `DamageRequest::apply` is: the same resolution at once with its outcome returned; every kit path queues. |
| Q20 | An active instance after its definition reloads? | What it placed stays as placed (its granted list, its modifiers, its duration); its period's payload reads the current definition, so damage tunes live and a changed `grant` still releases the old tag. |
| Q21 | Two ladder triggers for one target in one step? | The feed counts the tags of the effects it queued for the target earlier in the run as carried, so batched hits climb as split ones do. |

Each question takes its stated default; the owner reviews the plan on their own time (`D-150`).
