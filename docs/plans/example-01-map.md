## 2. Design

### 2.1 Scope and order

Seven rows, eight steps and the close. Step 1 is tests alone and warms the run. Step 2 goes before the lift because both change `level::spawn` and the lift's kept patch merges onto it once; the lift's own pit delta is the same on either base (A4). Step 5 puts every new marker in the map in one generator run, the kill row among them, so Step 7 reads it. Steps 6 and 7 leave the level's box as 01's two constants, which Step 8 then reads off the loaded map with the map's size, so `escaped` changes once (it goes) and not twice. A stopped step's dependents are in §6.

### 2.2 Tests are the spec

A test's asserts stand. A step may port a test's reads to the new owner (a follower for `Elevator`, the World's `PhysicsConfig` for `GRAVITY`, a marker for a coordinate, a step of the harness for a direct call of a removed system), and changes an asserted value only where its Moves name it. A ported test that could now pass on nothing gets a positive control (Step 1). New tests are the done-when's alone (the memory's rule for examples).

### 2.3 Tile box tests on `overlap` (Step 1, S-83)

`embedded`, the platforms' sweep and the elevator's sweep call `overlap(world, Shape::Aabb { half_extents }, centre, &SpatialFilter::new().with_bodies(false), &mut met)` and assert on `met.is_empty()`, as `elevator::filled` does. `start` settles through the curtain's fade, so steps have run and the tile cache is live before a test's first query (`tests/game/main.rs:135-143`, `:174-182`). Each test still asserts a positive control first, since a cold cache would pass every "meets no tile" assert: a box centred in a solid cell the test finds in the collision layer meets a tile, and one in the tests' sky meets none. The sweeps' messages keep the box, not the cell. The upper level's `solid` scan stays: it reads tile tops, not a box.

### 2.4 The map's objects named at their spawn (Step 2, S-144)

Core: `World::prepare_map_objects_named(map, origin: impl Into<Vec2>) -> Result<Vec<(PreparedPrefab, String)>, PrefabError>` becomes public, its doc naming the empty name; `spawn_area` and `spawn_room` call it as before. 01's `level::spawn` prepares the named form, spawns each with `prefab.with((SceneEntity { state_id: GAMEPLAY },))` in file order, keeping `(entity, name)`, then runs its loop of save IDs unchanged but for the `SceneEntity` insert, which goes; `object_names` goes. Entity IDs and the spawn order stand. What moves: each map object's archetypes (the prefab's alone, then with `Saved`, then with `SceneEntity`, become two), so the order in which a query meets archetypes of different prefabs may change: the suite passed on the prototype (A4), and the pit moves by §2.11. `W/7.13e-map-probes/stage-1-names.patch` is the prototype.

### 2.11 The pit's protocol

01's pit pin is exact. Steps 2, 3, 6 and 7 move it; each does this in place of the plain guard check:

1. With the step built and every other test passing, `cargo test --test game -- guards::` passes, or fails on `allocations`, `allocated_bytes` or `archetype_moves` alone.
2. The probe (`W/pit-probe/pit_probe.sh`: the guard's size histogram for `base` and `step`, then per-size backtraces for each size whose count differs; `diff.py` over the two) attributes every differing bucket to a site. `base` is HEAD's copy of every file the step changed that the run loads (`BASE_FILES`: its `src/` and `tests/` files and the changed `assets/` files; at Step 2 core's `assets/prefab.rs` is swapped by hand the same way). `U/testing/guard.rs`, which the probe patches, is restored from HEAD and compared (`cmp`) after each run. Nothing edits the tree under a probe.
3. The move is accepted when every bucket's site is in the step's allowance and each pinned line is within its bound; the evidence row quotes the old and new lines and the decomposition (size, count, site, cause).
4. Then `TUNGSTEN_GUARDS_WRITE=1 cargo test --test game -- guards::`, `git diff tests/game/guards/pit.json` showing those lines alone, and `cargo test --test game -- guards::` → exit 0.

Anything else stops the step (§6): another line moving (`spawned`, `despawned`, `events_sent`, the sprite maxima), a site outside the allowance, a bucket no backtrace explains, or a line past its bound. Three knock-on kinds are in every allowance: (a) a query's archetype bits regrown, or not, a 56 B copy and its 72 B `Arc`, at any system, when the step changes which archetypes exist; (b) a per-call slice list gaining or losing a doubled block at a system whose query matches an archetype the step adds or removes; (c) `particle_count_refresh_system`'s 4,096 B owner block. The evidence row names each knock-on bucket's kind and the archetype change behind it.

| Step | Own sites | Expected, measured (A4) |
| --- | --- | --- |
| 2 | kind (b) alone: each system whose query lists a map object's archetypes loses a block (`elements::systems::crate_hits`, `enemies::goblin::panics`, `state_machine::visit_all::<EnemyState>`, `platformer::Runner::run`, `HitboxRunner::run`, `toys::systems::bounds`), and `hierarchy::Walk::propagate` gains 2 × 256 B | 61,757 → 61,459 allocations; 63,900,393 → 60,103,913 B |
