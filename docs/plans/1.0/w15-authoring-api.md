## Context digest

- W15 is the game-facing authoring API: systems in named stages with constraints, engine features as plugins, tuple queries and bundles, and extracts that add up. All of it is public API the freeze covers ([w04](w04-api-freeze.md)), and every candidate is level C.
- Today `App::new` registers the engine's systems in one list, and the examples and the template add engine systems by hand in order: example 01's `setup.rs` lists `physics_step`, the sync, the squash pair, the shake and the camera, example 04 the last four, and the template's `game.rs` registers its one system by name. `World` has thirteen arity-named query functions; a spawn is `spawn` then one `insert` per component (the platformer's player takes a run of them); `set_extract_*` replaces the default extract outright, so example 01 draws its own tilemap.
- Both spikes ran on 2026-10-05 and the gate took every default: five closed stages with `fixed_update` before `update`, if-present constraints for the engine's cross-plugin couplings, `WindowSize` to core, `App` keeps the resources, the bench on an explicit set with the `particles` row re-owned (`D-128`); `query`/`query_mut` at W15b with two ledger rows and one budgeted step for the lone mutable column (`D-130`); no `Send`/`Sync` bound (`D-131`).
- Track C runs W15a, W3a, W15b, W3b, W15c, then the Phase 5 QA pass (amendment 18). W3b's `RigidBodyBundle` carries `PrevPosition` on W15b's bundle (`D-129`).
- Extract contributions cannot go through core, since `SpriteBatch`, `QuadInstance` and `TextSection` are render types (`D-007`, `D-016`): W15c's shape is an umbrella-side resource of contribution closures that plugins and games push into and the extract stage drains, and its decision is still to write.

## Scope

Moved verbatim from [criteria](criteria.md) §8.6 on 2026-10-06; section references now name their files. Folded in, as italic notes after the bullets they touch: the frame-loop gate's decisions (`D-128` on the stages, order and benchmarks bullets; `D-130` on the queries and bundles bullets; `D-131` on the tuple-queries bullet's R1 sentence) and implementation plan amendments 7, 8 and 16 (the stages bullet) and 18 (the done-when sketch).

Owner-picked on 2026-10-03: plugins with named stages, tuple queries and bundles. All of it is public API and lands before the freeze ([w04](w04-api-freeze.md)).

- **Stages and plugins.** Games add systems to named stages. Proposed: `startup`; `pre_update` (input, engine toggles, the state dispatcher); `fixed_update` (physics and opt-in gameplay, [w03](w03-frame-loop.md)); `update`; `post_update` (physics sync, hierarchy, animation, game feel, camera); then the engine's extract, render, audio and telemetry. Engine features become plugins (`PhysicsPlugin`, `CameraPlugin`, `GameFeelPlugin`, `ParticlesPlugin`, `TweensPlugin`, `DebugPlugin` and so on) collected in `DefaultPlugins`; a game leaves one out to replace it. The `Schedule` and `Plugin` live in `tungsten-core` ([criteria](criteria.md) §8.4), and `App` drives the schedule. This is W3's stage map: one design, one decision set. *Decided as proposed at the frame-loop gate (`D-128`): the five stages are closed; `fixed_update` runs before `update`, and gameplay that drives bodies opts into it to keep same-frame response; `PhysicsPlugin` is a core plugin and the display, debug, state, particle, tween, game-feel and camera plugins are the umbrella's; `WindowSize` moves to core; `App` keeps inserting the engine's resources whichever plugins run. W1 M3's routing stage joins `pre_update` after the state dispatcher, which is why M3 waits for W15a (implementation plan amendment 7). The acceptance game's repository starts from the template when W15a lands (amendment 8), and the template's `AGENTS.md` rule becomes systems by stage (amendment 16).*
- **Order within a stage.** Registration order alone does not compose: engine defaults, the kit and the game each add systems, and the platformer's list already depends on pairs such as `shake_tick_system` before `camera_update_system` and the squash trigger after ground detection. Every system has a name, and engine names are public constants that the freeze covers. A system may declare `before` and `after` constraints on names in its own stage. A stable topological sort resolves them, and ties keep registration order, so the schedule stays deterministic. An unknown name or a cycle fails at startup and names both systems. The resolved schedule of `DefaultPlugins`, the template and each example is snapshot-tested, so an engine reorder shows up as a test diff, and the systems overlay lists it. The kit declares its constraints against engine names, and the guide asks game plugins that touch engine features to do the same. *Decided (`D-128`): required `before`/`after` and `before_if_present`/`after_if_present` forms; the engine's cross-plugin couplings use the if-present forms, a plugin's own chains and a game's or the kit's constraints are required, so a typo fails at startup; `resolve` also fails on a duplicate name, and an unknown name's error says where the system is when it sits in another stage.*
- **Benchmarks keep their order.** `02_bench` wires engine systems itself. It starts from an empty plugin set, so no system runs twice and the digests stay. *Decided (`D-128`): an explicit `PluginSet` of the debug, display, state, particle and tween plugins, every row wiring `physics_step`, game feel and the camera by hand in its own order; a row that hand-wires an engine system registers the events it sends; the `particles` row re-owns its metric, since its untimed stage becomes named `post_update` systems, a benchmark-schema change the compare reports.*
- **Additive extracts.** By default the engine draws sprites and tilemaps. A game appends sprite and text contributions, and replaces the default only explicitly. Example 01's extract shrinks to what is its own (rainbow balls, outlined text, glows). *Not decided yet: contributions stay the umbrella's by construction, since `SpriteBatch`, `QuadInstance` and `TextSection` are render types (`D-128`); W15c writes the decision.*
- **Tuple queries.** `world.query::<(&A, &mut B, Option<&C>)>()` with `With<T>` and `Without<T>` filters replaces the arity-named functions, which stay deprecated until the freeze removes them. `slice::get_disjoint_mut` (stable since Rust 1.86) borrows two columns of one archetype mutably without `unsafe`, so the engine's first `unsafe` ([w02](w02-multi-core-rendering.md#facts)) should not be needed; a spike confirms it. R1's per-archetype column slices build on the same machinery. *Decided (`D-130`): the tuple API takes `query`/`query_mut`, with `query_filtered`, `query_mut_filtered` and the `_slices` forms, which is two ledger rows; the numbered functions stay `#[deprecated]` to the freeze; one budgeted step for the lone mutable column's loop layout. R1 left 1.0 at the gate (`D-131`); the slice forms stay for its return.*
- **Bundles.** `world.spawn_with((A, B, C))` and a command-buffer form, with a `Bundle` trait for tuples and game types. One archetype move per spawn instead of one per component, which is also the bundle-insert API in the [engine findings](../../perf/benchmarks.md#engine-findings). *Decided (`D-130`): as proposed, with `RigidBodyBundle` carrying `PrevPosition` (`D-129`).*
- **Resource access.** Beside today's `Option` accessor, a panicking one that names the missing type, for the resources `App` always inserts.
- **Done-when sketch:** the template and examples 01, 03 and 04 list no engine system; snapshot tests of the resolved schedules for `DefaultPlugins`, the template and each example; startup failure tests for an unknown name and a cycle; `ecs` and `churn` not regressed, since queries and spawns are their hot paths; benchmark digests unchanged; every arity-named query removed before the freeze. *The Phase 5 QA pass follows W15c (implementation plan amendment 18).*
