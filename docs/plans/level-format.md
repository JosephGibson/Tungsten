## 2. Design

### 2.1 The room file

A room is a JSON file in the manifest's `rooms` section (`"rooms": {"cave": {"path": "rooms/cave.json"}}`), read by `Room::from_json`: `version` first, so a version other than 1 fails before any other field; unknown fields fail; every error names its field path (`objects[3].at`), as screen files do. IDs, layer names and room IDs are `[a-z][a-z0-9_]*`. Coordinates are in cells from the room's top-left, y down.

```json
{
  "version": 1,
  "cell": [16, 16],
  "size": [40, 24],
  "tileset": "cave",
  "layers": [
    { "name": "art", "z": 1 },
    { "name": "solid", "kind": "collision", "layers": ["terrain"], "mask": ["player", "enemy"],
      "cells": { "7,19": "rock_crack", "8,19": null } }
  ],
  "shapes": [
    { "id": "floor", "rect": [0, 20, 40, 4], "tile": "rock", "layers": ["art", "solid"] },
    { "id": "ramp", "polygon": [[10, 20], [14, 16], [14, 20]], "tile": "rock", "layers": ["art", "solid"] },
    { "id": "bridge", "line": [[18, 12], [26, 12]], "tile": "plank", "layers": ["art", "solid"] },
    { "id": "pit", "rect": [30, 20, 3, 4], "tile": null, "layers": ["art", "solid"] }
  ],
  "objects": [
    { "id": "crate_1", "prefab": "crate", "at": [12, 19], "on": "floor" },
    { "id": "crawler_2", "prefab": "crawler", "at": [22, 11], "set": { "health.max": 30 } }
  ],
  "places": [
    { "id": "player_start", "point": [2, 19] },
    { "id": "arena", "rect": [20, 4, 16, 16] },
    { "id": "main", "route": ["player_start", [16, 15], "exit"], "by": "player" },
    { "id": "exit", "point": [39, 19], "to": "hall.west_door" }
  ],
  "post": [{ "kind": "bloom", "params": { "threshold": 0.8, "knee": 0.2, "intensity": 0.6, "radius": 1.0 } }],
  "ambient": [0.1, 0.1, 0.16],
  "budget": { "lights": 16, "objects": 1024 }
}
```

- **Top level:** `cell` (pixels, each at least 1), `size` (cells, each 1 to 4,096), `tileset` (a `tilesets` ID; needed once any layer exists), and the lists. `post` (a post stack as `PostPass` deserializes, `crates/tungsten-core/src/post.rs:353-407`), `ambient` (linear RGB, as `AmbientLight`) and `budget` (§2.7) are optional.
- **Layers:** each compiles to one runtime layer in list order. `kind` is `render` (default) or `collision`. A collision layer's `layers` and `mask` name physics layers, resolved through `PhysicsLayers` at compile (the Later line, S-175); without them it is `LayerPhysics::DEFAULT`, as a Tiled layer without its properties. A render layer's `z`, `unlit` and `tint` are its `LayerDraw`. `cells` are per-cell overrides keyed `"<col>,<row>"`: a tile by its sprite, or `null` for empty.
- **Shapes:** one of `rect` (`[x, y, w, h]`, cells), `polygon` (at least three vertices at integer cell corners; every edge horizontal, vertical, 45° or 2:1; simple, not self-crossing; and no cell crossed by two sloped edges, or by a sloped edge and another edge inside it, since a slope cell holds one face, `crates/tungsten-core/src/assets/tilemap.rs:210-248`) or `line` (integer points naming cells, both ends included, joined by horizontal or vertical segments, one cell thick); a `tile` (a tileset tile, named by its sprite, a style's brush included, or `null`, which erases); and the `layers` it paints (at least one). One-way, material and physics layer come from the tile and the layers (Q2).
- **Objects:** a `prefab` ID; `at`, the spawn position in cells (fractions allowed; `at × cell` is the entity's `Transform.position`, where its sprite's anchor is drawn, its top-left without one, as every spawn places one); `set`, overrides as dotted paths into the prefab's components, applied as a Tiled object's properties are (A5); `on`, a shape's ID: the surface it is anchored to, which a `move` of that shape carries.
- **Places:** one of `point`, `rect` or `route` (at least two items, each a point or a `point` place's ID). A `point` or `rect` with `to` (`<room>.<place>`) is a link: a door or socket. A `route` with `by` (a prefab ID) is checked as reachable by that prefab's mover (§2.7).
- **IDs** are unique across shapes, objects and places. An object's name in the World is `<room>.<id>` (`cave.crawler_2`), its save identity `SaveId::authored` of it, so two rooms may hold the same IDs (Q4, §5.1's `falls.crawler_2`).
- **The canonical form** (`Room::to_canonical`): screen files' writer moved to `core/canonical.rs` and shared, with one option rooms and tilesets set: an array of numbers prints on one line (`[10, 20]`). Defaults are left out, list order is kept, and the form reads back as the same room and is its own canonical form. Screen files keep their bytes (their tests run unchanged).
- **The schema:** `room::json_schema()`, draft 2020-12 like the screens', printed by `tungsten schema room`.

### 2.2 The tileset file

A `tilesets` entry names a file every room on it shares:

```json
{
  "version": 1,
  "tiles": [
    { "sprite": "rock", "style": "rock" },
    { "sprite": "rock_1", "style": "rock", "mask": 1, "weight": 2 },
    { "sprite": "rock_45_br", "style": "rock", "slope": "45 br" },
    { "sprite": "plank", "one_way": true, "material": "wood", "health": 20 },
    { "sprite": "arch", "whole": true }
  ]
}
```

Each tile has a `sprite`, which names it, and `TileProps`' fields as 7.8's Tiled properties take them (`docs/assets.md`'s Tilemap row), `broken` naming a tile by its sprite, plus `whole` (§2.10). A sprite appears at most once in a tileset: saves record an edited cell's tile by its sprite and restore the first entry holding it (`crates/tungsten-core/src/save/area.rs:41-44`, `:125-130`), so two tiles of one sprite would restore as one. A styled tile with a `slope` and no mask is one of its style's slope tiles, which the rasterizer picks (§2.3). Today such a tile is a second brush, which the one-brush rule refuses (`TileProps::is_brush`, `crates/tungsten-core/src/assets/tilemap.rs:307`; `:700-712`; `Styles::of`, `crates/tungsten-core/src/assets/terrain.rs:186-221`), so Step 5 narrows a brush to a styled tile with neither a mask nor a slope: a slope tile counts as its style for its neighbours' open sides, as any override does (`terrain.rs:15-23`), and the auto-tiler never picks it. `tungsten schema tileset` prints its schema.

### 2.3 Compiling a room

`Room::compile(id, &Tileset, &PhysicsLayers) -> Result<CompiledRoom, RoomError>`, pure and deterministic:

1. `TilemapData::new(cell, size)`; the tileset's tiles in file order with their props (`set_tile_props`); the layers with their physics and draws.
2. Each shape in list order paints each layer it names, a later shape over an earlier one: a brush makes auto cells, any other tile an override, `null` empty. A `rect` fills its cells; a `line` the cells its segments pass. A `polygon` fills each cell wholly inside it with its tile; a cell a sloped edge crosses takes, for a style's brush, the style's slope tile for that edge's rise and corner (a 45° edge one `45` cell per row, a 2:1 edge a `2:1 low` and a `2:1 high` cell per row), and for a plain tile the tile when the cell's centre is inside or on the edge. An edge at another angle, a cell two edges cross (§2.1), a style lacking the slope tile a cell needs and a shape past `size` fail naming the shape and the cell.
3. Each layer's `cells` overrides last.
4. One object layer, `objects`: each object as a classed `MapObject` (`id` its index plus 1, `name` `<room>.<id>`, `class` its prefab, `position` `at × cell`, `properties` its `set`), so the map-object check and spawn serve rooms unchanged (A4, A5); a `PrefabError::Object` maps back to `objects[i]`.
5. Places in pixels from the room's origin, routes resolved to points, and the settings, in `CompiledRoom` beside the map.

`World::insert_room(id, room)` compiles against the tileset the room names (`RoomRegistry::insert_tileset` registers one in code) and registers: the map in the `TilemapRegistry` under the room's ID (auto-tiled at `insert`) and the room in the `RoomRegistry` resource (documents, compiled rooms, tilesets, file paths). `level-generation` builds rooms through it.

### 2.4 Loading, spawning and names

- **Manifest:** `tilesets` and `rooms` sections (`path`), merged across manifests as every section is; a room's ID is its map's, so an ID in both `rooms` and `tilemaps` fails the load. The boot plan gains a unit per tileset and per room, run after the physics names and before the prefabs (A13), so the cross-checks that follow the prefabs cover rooms' tileset sprites and objects as maps'. The `RoomRegistry` is inserted only when a manifest lists a room or tileset, so a game without rooms allocates nothing new (02's boot guard, A19). A manifest reload loads them again (§2.8 patches the live rooms).
- **Spawn:** `World::spawn_room(id, origin, with: &B) -> Result<SpawnedRoom, AreaError>`, `spawn_area`'s path (A4) with `with` given to the instance and to each object as it is prepared (one archetype move), each object named `<room>.<id>` in area `<room>`. It sets `PostStack` and `AmbientLight` when the room has `post` or `ambient`, and leaves them otherwise. `SpawnedRoom` holds the instance and the objects by ID (S-144's engine part: spawned with their names). A room is live at most once: the `RoomRegistry` records the instance `spawn_room` spawned, and a second `spawn_room` of the room while that entity lives fails with a new `AreaError::Live` and spawns nothing, whether or not its objects still hold their names (`spawn_area` frees a dead entity's name, `crates/tungsten-core/src/save/area.rs:241`); several live copies of one template are `level-generation`'s, whose seeds give each copy its own names. Saves work as for any area (`D-230`): no save format change.
- **Places in the World:** `RoomRegistry::place(room, id)` in the room's own pixels, `SpawnedRoom::place(id)` in world pixels from its origin; a script reads them with the `place` probe (§2.6).
- **Check:** `tungsten check`'s content stage loads tilesets and rooms after stage 9's physics names, each error naming its file, room, ID and field path, then their objects against the prefabs, then §2.7's rules; their files join `manifest_files`, so none is loaded as a scene. `describe`'s `assets` lists `rooms` and `tilesets` by ID.

### 2.5 Commands, inverses and journals

A batch is a JSON array of commands, each an object with one verb. `Room::apply(&mut self, batch, &RoomContext) -> Result<Vec<RoomCommand>, RoomCommandError>` (named apart from the ECS's size-pinned `Command`, `crates/tungsten-core/src/tests/ecs/command_buffer.rs`) checks every command against the room as the earlier ones leave it and changes nothing unless all pass; it returns the inverse batch, which applied gives the room back byte for byte in its canonical form. `RoomContext` holds what validation reads beyond the room: the prefab IDs and the tileset (the CLI reads them from the manifests; the game from its registries). Component values in `set` are checked by `tungsten level check`, not by `apply`.

| Verb | Shape | Inverse |
| --- | --- | --- |
| `place` | `{"objects" \| "shapes" \| "places": entry, "index"?}`, or `{"layers": layer}` | `delete` |
| `move` | `{"id", "by": [dx, dy]}` or `{"id", "to": [x, y]}`; a shape carries the objects `on` it | `move` back |
| `set` | `{"id", "path", "value"}`; no `id` for the room's `size`, `tileset`, `post`, `ambient`, `budget`; `"layer"` for a layer's fields; `"set.<key>"` names one override; `null` removes an optional field | `set` the old value |
| `delete` | `{"id"}` or `{"layer"}`; objects `on` a deleted shape lose `on` | `place` at its index, `on` restored |
| `duplicate` | `{"id", "as", "by"?}` | `delete` |
| `paint` | `{"layer", "rect" \| "cells", "tile"}`: overrides; `"tile": null` removes them, the shapes showing through | `paint` the old overrides |
| `erase` | `{"layer", "rect" \| "cells"}`: empty overrides | `paint` the old overrides |
| `link` | `{"id", "to"}`, `null` unlinks | `link` the old target |
| `rename` | `{"id", "to"}`: the room's own references follow (`on`, routes, links to its own places) | `rename` back |

An error names the command's index and field (`commands[3].move.id: no entry `crawler_9`; did you mean `crawler_2`?`). A link to another room is checked by `tungsten check`, which reads every room; a rename leaves other rooms' links to the old name for it to report.

**Journals.** In the game, core's `RoomJournal` resource keeps each applied batch with its inverse per room, at most 64, for undo and redo (the `level` step's `undo`, the editor's later). A reload that changes a room's document, or reloads its tileset (a manifest reload included), clears that room's undo and redo, since their inverses were written against the room and tileset before it; a reload whose document equals the registry's (the editor's own save, later) keeps them. An undo or redo is applied as any batch is, so one that no longer validates fails and changes nothing. The CLI's `apply` appends `{batch, inverse, before, after}` (the room file's FNV-1a hashes) as one line to `target/tungsten/journal/<room>.jsonl` in the game's folder, cargo's ignored target folder (Q8); `apply --undo` applies the newest line's inverse and drops it, refusing when the file's hash is not that line's `after` (it changed outside the journal).

### 2.6 The CLI and the script steps

```text
tungsten level apply <room> <batch>   apply a batch (a file, or - for stdin), write the room canonically, journal it
           [--inverse <file>]          also write the batch that undoes it
           [--undo]                    undo the journal's newest batch instead
tungsten level query <room> [<id>] [--at <col>,<row>] [--json]
tungsten level describe [<room>] [--json]
tungsten level check [<room>...]
tungsten level render <room> -o <png> [--overlay <names>] [--size <w>x<h>] [--frame <n>] [--release]
```

- `<room>` is a manifest ID or a path. `apply`, `query` and `describe` read the files with the CLI's own core, as `schema` does, so they need no build: `query` prints an entry, or what lies at a cell (each layer's tile and whether it is auto, the shapes over it, the objects whose `at` falls in it, the places holding it); `describe` the rooms' layers and named things by kind, links with their targets.
- `check` runs the game's check (`TUNGSTEN_CHECK`, A11) and prints the room findings alone, each as `<file>: <room>: <id>: <path>: <message>`, exit 1 on any.
- `render` writes a script, as `render` does (A11): frame 2 `stage {}` and `room <id>`, the camera `{"fit": "staged"}` (its fit covering the room's map as well as the staged entities), the overlays, the capture.
- **Script verbs:** `room` (`{"frame", "room": "<id>"}`: `spawn_room` at the origin on the stage) and, in Step 10, `level` (`{"room", "apply": [...]}` or `{"room", "undo": true}`); the core probe `place` (`args: {"room", "id"}`): the place's world value in the room's live instance.

### 2.7 Checks and level rules

Core's rules run on a compiled room with the World's prefabs, sprites and physics names: the solid region of a body is the collision cells its contacts would meet, the runtime's rule both ways (the body's layers meet the terrain layer's mask and the terrain's layers meet the body's mask, `crates/tungsten-core/src/physics/step/mod.rs:270-273`), full cells as boxes and slope cells by their solid part (`Slope`, A2); one-way cells are not solid to these rules but count as ground for supports and reach.

- **Spawns clear:** an object whose prefab has a dynamic or kinematic `rigid_body` collider that is not a sensor must not overlap the solid region at its spawn (its collider at `position + offset`, read through a crate-visible reader of a `rigid_body` value in `physics/plugin.rs`).
- **Props supported** (`D-214` generalized): a prefab's new `support` field, `ground`, `under` or `wall`, judges an object by its sprite's drawn box (its size times the prefab's scale, placed by its anchor as the extract places it, `crates/tungsten-core/src/components.rs:136-150`), against its body's solid region, or every collision layer's for a prefab without a body: `ground` has the solid region within 2 px under at least 60 % of its bottom edge's columns and sinks at most 6 px into it; `under` has it within 2 px over 60 % of its top edge; `wall` within 3 px of its left or right edge over 60 % of its height. 01's pixel-level families, streams and groups stay 01's (7.13).
- **Budgets:** objects whose prefab has one of the light components the caller names (the umbrella's check names its `light`, A21) at most `budget.lights` (default 16, `D-061`'s cap), objects at most `budget.objects` (default 1,024) (Q11).
- **Routes reachable** (the kit, `motion::reach`, behind the umbrella's `kit` feature, A22): a route's `by` prefab with a `platformer_controller` is judged on what its own casts meet, the cells its `filter` admits (a cell's layers meet the filter's mask and none of its `without`, one-way cells as the filter takes them, `crates/tungsten-core/src/physics/query.rs:184-190`; `crates/tungsten-kit/src/motion/platformer.rs:846`), not the contact rule, and on stand cells (its body's box clear, ground under it): walks to a neighbour cell; one row up or down onto a slope cell only when its face is a floor by the controller's rule (its `slope_limit`, else the kit's `FLOOR_NORMAL_Y`, `crates/tungsten-kit/src/motion/slide.rs:24`) and not past its `slide_limit` (`crates/tungsten-kit/src/motion/platformer.rs:644-649`, `:984-990`); one row up onto a full cell only within its `step_height`; falls and jumps to any stand cell inside the arc its `jump_speed`, `air_jumps`, gravity (its own or `PhysicsConfig`'s) and `run_speed` reach, the arc's box clear of the solid region (one-way cells passed from below). A slope that is no floor by that rule is no ground. Coyote time and the jump buffer are left out, so the check errs short (Q7). A `top_down_mover` prefab, whose body the physics step moves, is judged by its body's contact rule on the cells its box fits, by 4-neighbour steps. Each leg is a breadth-first search from the stand cell under its first point to the one under its next; a point with no stand cell within 2 cells under it, and a `by` prefab with neither mover, are findings.
- **Where they run:** `tungsten check` (every listed room) and `tungsten level check` (the room findings, of the named rooms) (Q9). A finding names the room, the ID and the field path: `cave: crate_1: objects[0]: floats: 2 of 16 bottom columns have ground within 2 px`.

### 2.8 Live patching

A room file's reload, its tileset's reload, a manifest reload and a script's `level` step patch the room from its compiled form before to the one after, on the main thread (the watcher is `notify`'s thread, one of AGENTS.md's three). The registry takes the new document. Whether the live room changes is read from the compiled rooms (cells, the tileset's sprites and props, layers, objects, places, settings), not the documents, so a tileset's edit reaches every room on it, and a compiled room equal to the registry's patches nothing.

1. **Prepared whole first:** the new document (the file's, or the batch applied to a copy of the registry's) compiled, its tileset's sprites checked against the registered sprites as a tilemap's reload checks them (`crates/tungsten/src/asset_loader/reload.rs:304-317`), its objects checked against the prefabs (`check_map_objects`) and every object the patch will spawn prepared. Any failure leaves the registry's room and tileset, its journal and the live entities as they were (a tileset that fails keeps every room on it as it was): a reload logs the error and keeps the live room, as a tilemap's does (A3); a `level` step fails with it.
2. **The map:** when the size, cell, the tileset's sprites and props and the layer list are unchanged, each changed cell is written in place through a new `TilemapRegistry::set_authored_tile`, which writes it as `set_tile` does (journaled, re-tiled and re-outlined locally, `D-228`) and in the map as inserted, dropping that cell's edit and damage records, so a revert and a later save keep the file's cell; otherwise the map is inserted whole (history restarted, A1). Either way the map's object layer is replaced in the map and in its copy as inserted (`TilemapRegistry::set_authored_objects`), since the next spawn reads its objects from the map and then reverts it to that copy (`crates/tungsten-core/src/save/area.rs:218`, `:257`; `crates/tungsten-core/src/assets/prefab.rs:660`).
3. **Objects** of the room's live instance (one at most, §2.4), by ID: one gone is despawned; one added is spawned at once and given what the World's spawn inheritance derives from the instance (`D-170`; the umbrella registers `SceneEntity`, `crates/tungsten/src/plugins.rs:117`), then named; one whose prefab, `set` or `at` changed is despawned and spawned again under its name, so its save baseline is its new spawn's (a name takes its baseline once, `crates/tungsten-core/src/save/id.rs:250-253`, and a capture saves what differs from it, `crates/tungsten-core/src/save/world.rs:256-262`; a teleport would leave the old spot as the baseline). An object the run despawned (its name held by no live entity) stays gone: a patch never brings back what play removed, and the room's next spawn shows it.
4. **Places and settings** are replaced; `post` and `ambient` set again when they changed. A reload that changes the room's document or reloads its tileset clears the room's journal (§2.5); a `level` step's own patch keeps it.

The `level` step applies its batch through `Room::apply` (§2.5), then patches and journals it; it never writes the file (a script edits no asset), so the next reload of the file wins.

### 2.9 Prefab data

- **`extends`** (S-140): a prefab file names a base prefab. Its resolved form is the base's resolved file JSON with the variant's top-level fields over it, `components` merging per component member by member as an object property merges (`crates/tungsten-core/src/assets/prefab.rs:957`): objects recursively, arrays and scalars replaced. The registry keeps the file JSON of each prefab that extends another (none extra for one that does not), and every staged load's commit resolves them all again, so a base's reload reaches its variants; a missing base (with the nearest ID) and a cycle (the chain named) fail the commit. `describe` (version 3) lists `prefabs`, each `{name, extends, prefab}` resolved, and `tungsten describe <prefab>` prints one.
- **`scale`** (S-129): `[x, y]`, each finite and above 0, default `[1, 1]`: the spawn's `Transform.scale`.
- **`sprite.variants`** (S-58, 7.9's §2.16): sprite IDs checked as `asset_id` is; the pool is the sprite and its variants. A spawn shows one, picked by its save identity when it has one (the ID's FNV hash modulo the pool) and else by its spawn position's whole pixels; `save::name`, the flush's naming and a restore pick again for an entity holding `SpriteVariants`, so a named or saved spawn shows the same variant after a load with nothing saved. A room object is named before it is drawn, so it keeps its variant across runs.
- **`support`** (Step 9): `ground`, `under` or `wall`, read only by §2.7's rule.

### 2.10 Tiles drawn whole

`TileProps` gains `whole` (S-178): the tile draws at its sprite's own size with the sprite's bottom-left on its cell's bottom-left, as Tiled's image-collection tiles do. It is draw-only: out of the map's fingerprint, and a collision layer's cell stays one cell. The extract widens a map's cell range in view by its widest whole tile's extra columns to the left and its tallest's extra rows below, so a whole tile whose cell is out of view still draws the part that is in it. Only the tileset file sets it (Q5).

### 2.11 Engine settings as data
