## 2. Design

### 2.1 The engine's two identities (Step 1)

01 needs two things core lacks (A6): an identity for an entity whose record the game writes itself, and a spawn that takes the run's next ID now without a saved source. Step 1 adds, in core, amending `D-230` by the step's decision:

- **`save::take_id(world) -> Option<SaveId>`:** the run's next ID, from the counter the flush uses; `None` without save state or past `AUTHORED`.
- **`Saved::kept(id) -> Saved`:** a kept identity, a `Saved` with no area and no prefab that no naming made. Its holder's references resolve by its ID in a capture and a restore, the kit orders it by its ID, and a capture writes no record of it (A7): the game saves and restores its holder, spawning it back with `Saved::kept(id)` before `restore_world`, whose second pass then resolves references to it. A kept identity in a World without save state changes nothing (`saving` stays false).
- **`PreparedPrefab::saved(self, world, area) -> Self` and `save_id(&self)`:** while the World saves, the prepared spawn takes the run's next ID now as a spawn of its prefab in `area` (a `Saved` with that prefab), recorded in its run so `spawn` or `CommandBuffer::spawn_prefab` gives it in the spawn's one archetype move, and shows the sprite variant the ID picks; without save state it does nothing and `save_id` is `None`.
- **The flush keeps a given identity:** a spawn from a saved source whose own run gave it a `Saved` keeps it, and the counter does not move (`ecs/world.rs`'s `derive_from` checks the target first).

Nothing is registered and no default moves: a World that never names is as before, so the physics hashes, the kit's pin, 02's pins and the template hold (§5).

### 2.2 01's identities (Steps 3 and 4)

- **Step 3, a rename with no behaviour:** 01's `SaveId` component goes; its entities carry core's `Saved` and 01 reads `Saved::id()`, core's `SaveId` value in every field that holds an ID (the same JSON). The map's saved kinds and the player take `Saved::kept(SaveId::authored(name))`, each runtime spawn `Saved::kept` of 01's counter. Every caller of the counter goes through two helpers in `shared`, `take_id(world)` and `next_id(world)`: the spawn sites, `run/pit.rs`, `toys/systems.rs`' flare and spray seeds, and the tests' own spawns (A24), so Step 4 changes the helpers' bodies alone. Nothing names, so the World does not save: the kit's order, the flush and every test hold; at most the pit's bytes move, `Saved` being wider (§2.9).
- **Step 4, the engine's identities:** the player is named `player`, global, and each saved map object by its name in area `ex10_level` with `save::name`, once the run start's setup is done (after `dummy::start`, `enemies::start`, `drops::start` and the player's spawn), so each baseline is the set-up object (Q3). A load's player spawns at the map's spawn, as a fresh run's, and is named there, so its baseline is the fresh spawn's and a saved point is a patch over it (A25); `restore_world`'s position patch then moves it, in the same `on_enter`, before the camera's first frame. The helpers take `save::take_id` and read `SaveState::next_id`, and `SaveIds` goes, so a kept spawn, a recorded one and the kit's never share an ID. The kit's spawns from a saved source take the next ID at the flush and are the engine's records (A10): the bullets, fire missiles and rolled orbs, whose `adopt` systems key on a marker of their own (`Joined`), not on a missing identity. Gameplay's exit drops the run's identities, as the template's does (`Saved` stripped, `SaveState` removed), so a new run's names are free. The kit now orders 01's work by save ID (A9).
- **The named move whole in Step 4:** once a named entity's components are registered, its state is the World save's alone; no step keeps its record beside a patch, since a status setter would build on the restored status again (A21).

### 2.6 What does not move

- **The kit's `Emitter`** (A16): a restored projectile spawns from its prefab with no emitter, and its hits still spare its `Source`'s entity, which for 01's bullets, missiles, flasks and snowballs is the entity they were spawned from. A spawn of a spawn in flight at a save would lose its emitter; none of 01's saved kinds is one. Step 5's census names `Emitter` as the one type a loaded projectile lacks, and a test holds what it served: a fire missile and a bullet loaded beside their caster spare it. A Later line (Step 7).
- **The free spot's band** (A20): a named or recorded body `restore_world` places goes to its free spot when it overlaps a solid past the band. A test that shows a loaded body moved past its tolerance stops the step (§6); the band is known issue 61's.
- **Kit-made presentation:** a kit spawn from a saved source is recorded unless prepared unsaved (`D-230`'s Q6). 01's data spawns none but A10's three kinds; Step 4's test pins the set of recorded prefabs, so a cue prefab added later shows there.

### 2.7 The map's props as objects (Step 6)

`tools/level.py` writes the map's loose iron, crates, kegs and stones as classed objects on a layer of their own, each named (`iron_<n>`, `crate_<n>`, `keg_<n>`, `stone_<size>_<n>`, unique), each keeping the variant today's fresh run picks for it (Q8), in place of the four marker kinds (A17). The level spawns them as it spawns the enemies; 01 names them with the other saved kinds, so a load patches them or lists them gone, and `run/mod.rs`'s marker loop goes. Their authored IDs leave the run's counter, so a fresh run's runtime IDs start lower; tests that read a runtime ID by number follow. It needs Step 5's prop registrations.

### 2.9 Perf and pins
