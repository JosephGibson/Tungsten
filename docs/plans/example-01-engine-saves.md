## 2. Design

### 2.1 What a save holds that a load can give back (Steps 1 and 2)

A capture writes a moving body's drawn point as its transform's position (A1, A2); a restore teleports it to its saved `position`, then puts the saved transform, which the next `physics_sync` draws again at `Position` (A4), so a load's recapture writes another point for every interpolated body that moved in its last frame (A5). Chemistry's queue writes the entries whose receivers have no save ID, which its load drops though the uninterrupted run still takes them under its cap, and orders its entries by entity index, which a load does not keep (A27, A30, §2.10). A form reads its value alone (A3), so neither can be fixed in the form. Steps 1 and 2:

- **`SaveOptions::capture_as(read: fn(&World, Option<Entity>, &T) -> Option<T>)`** (core, Step 1): the value a registration saves in place of the live one, read with the World; the holder is `Some(entity)` for a component and `None` for the resource; `None` back saves the live value. `Typed::to_value` calls it, and `save_refs` and `keys` read the same value, so a payload and its references never part (A28); a capture's named patches and spawn records, `save::name`'s baseline, a restore's patch base and the resources all read it (A3).
- **The app's `transform`** (Step 1) registers with `capture_as(body_transform)`: an entity with a `Position` saves its transform with `Position` as its position, its rotation and scale as they are; one without saves its transform as before. Of the known issue's three ways this is the second; the others are not taken: the position left out of a body's save (an optional field, a version, and a put that keeps the live position, which a form cannot do), and `PrevPosition` saved with the frame's alpha (the alpha is `Time`'s accumulator, unsaved, and the drawn point is presentation nothing reads back).
- **`save::check_world(world, &save) -> Result<RestoreReport, RestoreError>`** (core, Step 1): `restore_world`'s checks (format, counter, versions, each area's plan, the resources' values) and nothing else, factored out of `restore_world`, which runs them first as before (A29): no entity, component, resource or save state changes; preparing a recorded spawn's prefab may intern its sprite names in the asset registry, as `restore_world`'s checks do today and as any spawn of that prefab would (A31). A game that stages entities before a restore checks first and stages only a save that passes.
- **Chemistry's queue** (kit, Step 2): its load keeps an entry whose entity receiver did not resolve (despawned or never saved at the capture) as a dead one, out of the index and the counts, so a run takes it under the cap, skips it and counts it in `ran`, as the uninterrupted run does the entry on its despawned receiver (A30; `pending` matches too); and it registers with `capture_as`, a copy written in the run key's order (age, depth, a named receiver by save ID, then an unnamed one, then cells, stimulus name; ties in slot order), so a World whose entities took other indices writes the same queue and a loaded queue's dead entries, all one placeholder, keep their saved order. Its credit stays a reference, an unnamed one loading as none (A27). The run order does not change; an unnamed live receiver's entry loads dead, its receiver not being in the save; the kit's other saved queues stay as they are (Q10, Q12).
- **What holds:** `SavedTransform`, its version 1 and every older save, which loads as before (its drawn point put, then drawn again at the next `physics_sync`); chemistry's saved form and version, a save written before Step 2 loading with its dead entries kept; the restore's order and results; `spawn_position`, which now reads the body's own point. Rotation stays as it is: `physics_sync` writes it only once a step turns a spinner, and `spin` saves its `prev_angle`, so a held load's recapture writes the saved rotation back (the probe's round trips held on it; Q9).
- **What moves:** a saved interpolated body's `transform.position` values, so 02's `saves` row's `bytes` counter and digest (information, `D-226`) and at most `guards_saves`' `allocated_bytes` by the text's length (A6); a saved chemistry queue's order, and a loaded one's entries on unnamed receivers, kept dead instead of dropped. The hooks run in a capture alone: one `Position` lookup a transform holder, and a copy of chemistry's queue with a save-ID read an entry. The `saves` row, which captures 12,000 spawns a frame, takes the lookups; the close's quick sitting quotes it as information.

### 2.2 01's identities (Step 3)

- **The engine's identities:** the player is named `player`, global, and each saved map object by its name in area `ex10_level` with `save::name`, once the run start's setup is done (after `dummy::start`, `enemies::start`, `drops::start` and the player's spawn), so each baseline is the set-up object (Q3). A load's player spawns at the map's spawn, as a fresh run's, and is named there, so its baseline is the fresh spawn's and a saved point is a patch over it (A24); `restore_world`'s position patch then moves it, in the same `on_enter`, before the camera's first frame. The helpers take `save::take_id` and read `SaveState::next_id`, and `SaveIds` goes, so a kept spawn, a recorded one and the kit's never share an ID (A8). The kit's spawns from a saved source take the next ID at the flush and are the engine's records (A14): the bullets, fire missiles and rolled orbs, whose `adopt` systems key on a marker of their own (`Joined`), not on a missing identity. Gameplay's exit drops the run's identities, as the template's does (`Saved` stripped, `SaveState` removed), so a new run's names are free. The kit now orders 01's work by save ID (A13).

### 2.3 The format and the restore order (Steps 3 to 5)
