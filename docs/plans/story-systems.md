## 2. Design

### 2.1 8.1 in three plans

8.1's row is three plans' work, split by what each stands on, each written from the tree of its day when the one before it closes:

1. **`story-systems`, this plan:** conditions, the interactor (P7-3), conversations and the box (P8-1), quests and the journal (P8-2), typed text (P8-5). Conditions come first: the second plan's `requires` and the third's schedule gates read them.
2. **Items and shops:** items, stacks, the inventory with drag and drop between widgets and shops (P8-3), equipment as statuses (Q17), rolled instances with local and global lines and the ARPG design's §16 check, "an item from §4.6's JSON equips, shows its lines and saves round trip" (PA-12), ground labels by rarity (PA-13), the grid layout as `D-124`'s first user (S-162), tooltips and popups (§5.9), images in screen files; 8.7 waits for it.
3. **Cutscenes, the clock and areas:** timelines on 7.18's rigs and blends that play this plan's lines (P8-4), a world clock with phase events and schedules placing an NPC while its area is unloaded (P8-6), loading between areas on 7.9's saves, sliced on the main thread (P8-7), the cone light (P8-17).

Each takes its own recipes, sketch, row and art. The split lives in `ROADMAP.md`'s `phase-8` line from this plan's commit, since the plan is deleted at its close.

### 2.2 Where it lives

- **The kit** (Q9): a `story` domain (`story/mod.rs`, `condition.rs`, `dialogue.rs`, `runner.rs`, `say.rs`, `quests.rs`), and `overlap/interact.rs`. Four plugins join `KitPlugins::set()` before `KitDebugPlugin`, in this order: `InteractPlugin`, `DialoguePlugin`, `SayPlugin`, `QuestsPlugin`. Each system gates on `World::has_any` of its holder or its resource's presence first (`D-247`), so 01's pit and tour and the template run no new query (A23).
- **Core:** the public prompt text (Step 1), the hooks after a restore (Step 3), the reveals (Step 4), the typed-text record and the text field (Step 8).
- **Render:** a revealed command's areas (Step 4).
- **The umbrella:** `story.rs` behind `kit`, `StoryUiPlugin`, which a game adds: the box state, the dialogue and journal bindings (Steps 5, 6); the bridge's characters (Step 8).

### 2.3 Conditions (Step 1)

`Condition`, in `story/condition.rs`: one object with one key, closed, no expressions.

| Form | Data | Holds when |
| --- | --- | --- |
| flag | `{ "flag": "nets_torn" }`, or `{ "flag": { "name": "nets_torn", "target": "game" } }` | the target's `Flags` has it |
| counter | `{ "counter": { "name": "trust", "min": 3, "max": 9, "target": "other" } }`, one or both bounds, inclusive | the target's count, 0 when it holds none, lies in them |
| stat | `{ "stat": { "name": "vigour", "min": 20 } }`, one or both, finite, `min` ≤ `max` | the target's `Stats::get` lies in them; none when it has no such stat |
| tags | `{ "tags": { "all": […], "any": […], "none": […], "target": "other" } }` | the target's tags pass the filter |
| all, any | `{ "all": [ … ] }`, `{ "any": [ … ] }`, each at least one | every one, at least one |
| not | `{ "not": { … } }` | the inner fails |
| quest (Step 6) | `{ "quest": { "id": "lamplight", "is": "active", "stage": "light", "target": "other" } }` | §2.9 |

- `target` is `self` (the default), `other` or `game`, the words and default of the cue actions beside them (A3); `game` reads the game's resources and suits `flag`, `counter` and `quest` alone (the load refuses it on `stat` and `tags`). A target that is absent or dead holds no form, so a `not` of it holds.
- `Condition::holds(&self, world, subject: Option<Entity>, other: Option<Entity>) -> bool` reads the World and allocates nothing; nesting is at most 8 deep and a list at most 32 long, refused past either at parse.
- The load check: a `stat` names a declared stat (a new `pub(crate) fn check_stat` over `bounds_of`, A24), a `tags` form's names are declared (`check_declared`), a `quest` names a `quests` entry and its stage; flag and counter names stay undeclared, as the cue actions' are (Q-e).
- Described: the one-of shape `condition` and `flag_condition`, `counter_condition`, `stat_condition`, `tags_condition`. It lands with its first user, the interactable's `when`, since describe refuses a shape no field names (A10).

### 2.4 The interactor and the interactable (Step 1)

- **`interactor`** (`Interactor`, on whoever interacts): `{ "slot": "interact", "reach": 48, "font": "engine_mono", "size": 14, "color": [1, 1, 1, 1] }`, all optional with those defaults: the `Intent` slot it presses, its reach in px, and its prompt's face, size and linear colour. `focus()` gives the interactable it would use now.
- **`interactable`**: `{ "verb": "Talk", "radius": 0, "offset": [0, -16], "who": { "all": ["team.player"] }, "when": { … } }`, `verb` required: the prompt's word, a radius added to the interactor's reach, the prompt's shift in UI units off the centre, a tag filter on the interactor and a condition (subject the interactable, other the interactor).
- **`interact`** in `Phase::Intent`, after `action_input`: for each interactor in `order_of`'s order, the nearest interactable whose centre lies within reach plus radius of the interactor's (A24), whose `who` passes and whose `when` holds becomes its focus, ties to the lower order key; a `pressed` slot with a focus sends `Interacted { interactable, interactor, position }`, once a press. One scan of the interactables a step, shared by every interactor.
- **`interacted`**, the 26th kit cue event: the reactor reads `Interacted` through a cursor as `zone_entered` does, subject the interactable, other the interactor, at the interactable's centre (`amount` no, `other` yes, `kinds` no).
- **The prompt**, `interact_prompt` in `Phase::Present`: each interactor's live focus gets a world label at its centre plus `offset`, pivot (0.5, 1), outlined 1 unit in near black, reading `{action:<action>} <verb>`, the action the interactor's `action_input` binds to its slot, else the slot's name. Core's resolution becomes public as `ui::prompt::PromptText` (`new(template)`, `text(&mut self, Option<&ActionMap>, InputDevice) -> &str`, rebuilt only when the device kind or a named action's bindings move, as `Prompt` is today); the kit keeps one an interactor and rebuilds it when the focus changes.
- Both are unsaved: `interactable` is rule data, `interactor`'s focus is found again each step.

### 2.5 Speakers and conversations (Step 2)

Two kinds in `story/dialogue.rs`, one entry a file (`D-171`):

```json
// data/speakers/keeper.json, the `speakers` entry `keeper`
{ "name": "Old Tamsin", "portrait": { "neutral": "keeper_face", "worried": "keeper_worried" }, "pace": 40 }
// data/dialogue/keeper_evening.json, the `dialogue` entry `keeper.evening`
{
  "speaker": "keeper",
  "start": "greet",
  "nodes": {
    "greet": { "lines": ["Evening, warden.", { "speaker": "warden", "text": "Evening." }], "next": "offer" },
    "offer": {
      "lines": [{ "text": "The lamp by the steps is out again.", "mood": "worried" }],
      "choices": [
        { "text": "I'll light it.", "do": [{ "flag": { "name": "lamp.promised", "target": "game" } }], "next": "thanks" },
        { "text": "Who keeps the lamps?", "when": { "not": { "flag": { "name": "lamp.asked", "target": "game" } } },
          "do": [{ "flag": { "name": "lamp.asked", "target": "game" } }], "next": "offer" },
        { "text": "Not tonight.", "back": true }
      ]
    },
    "thanks": { "lines": ["Bless you."] }
  }
}
```

- **A speaker:** `name` (shown), `portrait` (a sprite ID, or moods to sprite IDs, `neutral` the default mood; optional), `pace` (characters a second the box reveals at, above 0, 40 by default).
- **A conversation:** `speaker` (the default for its lines), `start` and `nodes` by name (`[a-z][a-z0-9_]*`). A node has `lines`, `do` (cue actions run as it is entered), and at most one exit: `choices`, `next` (a node) or `branch` (a list of `{ "when", "next" }`, the first that holds); none ends the conversation. A line is its text, or `{ "speaker", "text", "mood", "when" }`, skipped when its `when` fails. A choice has `text`, `when`, `do`, `next` (none ends) and `back` (the choice Cancel takes; at most one a node).
- **Bounds:** at most 256 nodes, 32 lines and 8 choices a node, 2,000 characters a text.
- **Structural checks,** in the entry's `TryFrom`, each naming its node, so a parse error reads `nodes.offer.choices.2.next: …`: `start` and every `next` and `branch` target name a node; every node is reachable from `start`; a `choices` list holds a choice with no `when` and a `branch` ends with an entry with no `when`, so a shown node always has a way on; a node with no choices and no line free of a `when` may show nothing, so it counts as a jump, and the jumps form no cycle and no chain of more than 63, so a call enters at most 64 nodes, the runner's bound (§2.6), and checked data never loops unseen nor reaches the bound.
- **World checks,** in the kind's check (A9): each speaker names a `speakers` entry and each `mood` one of its portraits, each portrait a loaded sprite, the conditions' names (§2.3) and each `do` list's actions as `check_actions` checks a cue event with an other and no amount, through a new `pub(crate) fn check_list` in `cues.rs`; a failure is one `MissingAsset` at its field path, `nodes.offer.lines.0.speaker` (`kind` `"speaker"`). A speaker's check: its portraits name sprites the registry knows, loaded or interned; the recipes' speakers carry none, and the umbrella's box tests intern theirs as the recipes intern their prefabs' sprites (`crates/tungsten/src/tests/kit_recipes/mod.rs:67-83`).
- Described: kinds `speakers` and `dialogue`, entry shapes `speaker` and `conversation` (on describe's list of entries no field names), `dialogue_node`, `dialogue_line`, `dialogue_choice`, `dialogue_branch`.

### 2.6 The runner and the `dialogue` action (Step 3)

The box covers gameplay, and the clock holds under it (A14), so the runner is calls, not a system, and a list runs at the call:

- `Dialogue`, a World resource the first `talk` inserts, holds at most one `Talk`: the conversation, the speaker and the listener, the node, the line index and the shown choices.
- `tungsten_kit::talk(world, id, speaker, listener) -> bool`: refused while a talk runs, for an unknown ID or a dead entity; else enters `start`. `Dialogue::advance(world) -> bool` goes to the next line whose `when` holds, else past the lines; refused while choices show. `Dialogue::choose(world, index) -> bool` takes a shown choice: its `do`, then its `next` or the end. `Dialogue::end(world)` ends at once. `Dialogue::current()` reads the `Talk`: `line()` (the speaker's ID and name, the text, the portrait sprite by mood) and `choices()` (each shown choice's index and text).
- **Entering a node** runs its `do`, then shows its first line whose `when` holds; past its lines, its choices whose `when` holds show, its `next` or first holding `branch` entry is entered, or the talk ends. A call enters at most 64 nodes, ending the talk with a warning past them, a bound the jump check (§2.5) keeps data from reaching.
- **Lists run at the call**, through a new `pub(crate) fn run_list(world, actions, subject, other, at)` in `cues.rs`: a second `Reactor` in a `ListRunner` resource, taken out around each call, applies each action as the cue system does and finishes as `react` does (despawns into the command buffer, words to the labels); its sound clock reads `Time::real_elapsed`, since the game clock holds. A conversation's lists run with the speaker as subject, the listener as other, at the speaker's centre. It is re-entrant: a list that a running list starts (the rewards a `quest` action brings, §2.9) joins a `ListQueue` resource, which stays in the World while the reactor is out, and the outermost call drains it in order before it returns, so every list a call starts has run when the call returns.
- **What a list does at once,** since each action keeps the cue system's own path: `counter`, `flag` and `quest` write their state, which the next condition reads; `say` and `sound` show and play at once; `shake`, `burst`, `flash`, `squash`, `clip` and a raised `camera` rig with a blend start at once and move on the game clock, so under a held clock they hold until play resumes (a rig with no blend cuts at once); `prefab`, `roll` and `despawn` land at the frame's flush, which runs under a held clock; `effect` resolves at the next fixed step, so while the box holds the clock it waits for play, and a condition in the same conversation reads the state before it. The rustdoc and the `dialogue` kind's description say so.
- **What a list may not hold,** refused at load by `check_list` (A27): `ability`, whose `ability_used` cue rides an event the frame drops while the clock stands still, so a conversation would spend its cost and lose its cues; `loop` and `stop`, whose wants only the cue system's own pass keeps; a `label`, which needs an amount no list carries.
- **One call drains at most 64 lists;** past that the rest are dropped, traced and warned once, so rewards that fan out (§2.9) cannot freeze a frame.
- A talk whose speaker or listener has died ends at the next call; `DialogueStarted` and `DialogueEnded { speaker, listener, conversation }` are plain events, no cue events, since a cue under the box would run only once the box closed.
- **A restore ends a talk.** `restore_world` writes saved state and leaves unsaved resources (A26), so core gains `save::on_restore(world, name, fn(&mut World))`: named hooks in a `RestoreHooks` resource, inserted by the first, run in registration order once a restore has applied and never after a failed one, a second registration under a name replacing the first. `DialoguePlugin` registers one that ends a running talk without its lists and sends `DialogueEnded`, so the box pops; `SayPlugin` (Step 5) one that clears the barks.
- **The `dialogue` action,** `{ "dialogue": "keeper.evening" }`: `talk` with the subject as speaker and the other as listener, skipped and traced without an other or while a talk runs; refused in a world cue. Its field is a `DataRef` to the `dialogue` kind, checked at load. This action, `say` and `quest` box their payloads where they pass today's largest kind, so `CueAction` keeps its size in every cue list 01 spawns.
- Not saved (Q-f): a capture during a talk holds what its lists did; a restore opens none.

### 2.7 Text revealed without relayout (Step 4)

- **Sizes first.** The app takes `UiTree` out and inserts it again at every paint (A25), so a field on the tree or on `Node` would move `allocated_bytes` in every guard that paints a UI; the reveal keeps out of both, and `PaintCommand` keeps its variants.
- Core: `UiReveals`, a resource `UiReveals::of(world)` inserts on first use, as `UiBindings::of` does: `set(label, Option<u32>)` shows the first `n` characters of a label's (or a button's label's) laid-out text, `None` every one, and raises a revision; nothing lays out. `PaintList` gains `reveals: Vec<(TextNodeId, u32)>`, empty unless a label reveals, so it allocates nothing elsewhere; `UiReveals::write(&self, tree, list)` fills it under each label's base text node (`TextNodeId::base`), and render looks a command's count up by its node's base, so the outline and shadow copies of a label with coloured spans, which draw its plain view (`id.plain()`, A16), reveal with it. The app calls it after its paint step, every frame the reveals' revision or the paint moved, and `UiHarness::paint` does as the app does.
- Render: `batch_areas` draws a command whose node `reveals` names as at most two `TextArea`s over one buffer, from its layout runs: the runs wholly revealed under one rectangle, and the run that holds the `n`-th character under a band from its top to its bottom, to the right edge of its last revealed glyph; `n` past the text draws as today, and 0 draws nothing. A right-to-left run reveals whole. The count joins the batch's `CommandSignature`, so a moved count prepares that batch again and nothing lays out.
- The guard: `a_revealing_label_lays_out_no_root`, 60 frames of a climbing count with `layout_totals` unchanged and each frame's list carrying its count.

### 2.8 The dialogue box and barks (Step 5)

- **`StoryUiPlugin`** registers the bindings and the screen `dialogue` (`screens::register`), and adds `dialogue_open` in `update`: while a `Talk` runs and no box is up it opens one with `screens::open(world, "dialogue")`, which needs the game's `ui_screens` file `dialogue` (a root modal on the popup layer); without one it warns once and the talk stays open for the game's own Rust.
- **Bindings:** text `dialogue.speaker`, `dialogue.text`; visible `dialogue.reading`, `dialogue.choosing`; rows `dialogue.choices` (each row's `text` field); mount `dialogue.portrait`, an image the box sets per line and collapses without a portrait; actions `dialogue.continue` and `dialogue.choose` (the row is the choice's index).
- **The box,** a `GameState` on the file's root through `ModalScreen::adopt`: each line sets the `text` node's text once and its count in `UiReveals` from 0, climbing at the speaker's `pace` on real time; `dialogue.continue` (Accept, or a click on its button) shows the rest of a revealing line, else advances; a choice row's activation chooses; Cancel takes the node's `back` choice when it shows, else does nothing; the talk's end pops the box. The covered state's `holds_clock` decides whether play stops (Q-b).
- **`say`,** `{ "say": "Fog's coming in." }` or `{ "say": { "text", "seconds": 2.5, "font": "engine_mono", "size": 14, "color": [1, 1, 1, 1], "offset": [0, -16], "target": "self" } }`: the target's bark, replacing its last, in a `Barks` resource the first `say` inserts; `say_tick` in `Phase::Present` draws each live bark as an outlined world label over its entity's centre, fading over its last 0.2 s, aged by the game clock so a bark holds under a pause; at most 64, the oldest dropped; refused in a world cue.

### 2.9 Quests and the journal (Step 6)

```json
// data/quests/lamplight.json, the `quests` entry `lamplight`
{
  "title": "Lamplight",
  "start": "light",
  "stages": {
    "light": { "journal": "Light the lamp by the steps.", "objectives": [{ "text": "Lamp lit", "when": { "flag": { "name": "lamp.lit", "target": "game" } } }], "next": "report" },
    "report": { "journal": "Tell Tamsin it burns.", "rewards": [{ "counter": { "name": "coins", "add": 5, "target": "game" } }] }
  }
}
```

- **A quest:** `title`, `start`, `stages` by name, each with `journal` (its text), `objectives` (each `text` and a `when` condition), `next` (none completes the quest) and `rewards` (cue actions run as the stage completes). The parse checks `start` and each `next` name a stage, every stage is reachable and the stages form no cycle; the kind's check holds the conditions and the rewards as §2.5 does, but as an event with no other, since rewards run with none, so a reward or an objective naming `target: other` is refused at load.
- **`Quests`,** a component (`quests`, on a holder such as the player) and the game's resource, as `Counters` are: each quest's status (`active`, `done`, `failed`) and stage, saved both ways at version 1; a restored stage the data no longer holds restores at the quest's `start` with a warning.
- **`quest` action,** `{ "quest": { "id": "lamplight", "op": "start", "target": "other" } }`: `op` `start` (the default; a quest started once stays), `advance` (the stage completes), `fail`, or `"stage": "report"` (straight there, no rewards). **`quest` condition:** `is` `new`, `active`, `done` or `failed`, and `stage`, active at that stage.
- **Completing a stage** moves the quest to its `next` (or done) first, then runs the stage's rewards through `run_list`'s queue (§2.6), so a reward that advances its own quest completes the next stage, not this one again. Each queued list carries its depth, one more than the list whose action queued it; a `quest` action in a list 8 deep is skipped and traced, and a call drains 64 lists at most (§2.6), so self-advancing rewards, quests that advance each other, a reward that jumps its quest back and rewards that fan out into many lists all stop. `quest_tick`'s one stage a quest a step bounds the automatic completions alone; actions advance at once.
- **`quest_tick`** in `Phase::React`, after `cues` and before `kit_despawn`, so a count a cue wrote this step counts: for each holder in `order_of`'s order, then the game's, every active quest whose stage has objectives that all hold completes that stage, one stage a quest a step. Rewards run through `run_list` with the holder as subject and no other, so on the game's quests an action that needs a subject is skipped and traced. A completed, failed or moved quest sends `QuestChanged { holder, quest, status, stage }`.
- **The journal:** rows `quests.active` (fields `title`, `journal` and `objectives`, one line an objective, "Lamp lit 0/1": a lone `counter` condition with a `min` shows its count against it, any other form 0 or 1) and `quests.done` (`title`), reading the holder `JournalView` names, else the game's; `tungsten::story::open_journal(world, holder)` sets it and opens the game's `journal` screen file as a data screen.

The walkers' presses are the bench's own `Intent` writes in `Phase::Intent`, before `interact`. Presets `min` (2 walkers, 40 interactables, 8 holders of 4 quests) and `default` (8, 400, 64 of 8).

### 2.11 Typed text and the text field (Step 8)

- **Input:** `RawInput::Text { ch: char }`, one record a character in arrival order, so the stream stays `Copy` and `RawInput` its size; `InputState::type_text(&str)` records each non-control character, and `typed()` reads the frame's text back from the stream, so `InputState` gains no field. `apply_key` returns whether the press reached the input, and the bridge records a pressed `KeyEvent`'s `text` only then, so a synthetic press, a key held across a focus return (suppressed until release, A18) and a repeat of a key never pressed type nothing, as they press nothing; dropped-input frames drop both. IME stays later.
- **`WidgetKind::TextField`,** the eighth kind (role `TextInput`), in a new `ui/field.rs`: a focusable, interactive box holding one label, its value or its placeholder in the theme's muted text colour, as a button holds its caption, so layout measures it as it measures any label (A18); it wears the button's kind style. Its state, the value, a caret (a character index), an optional `max` characters, the value on focus and its scratch node, is a `Control::Field(Box<FieldState>)`, boxed so `Control`, `Node` and `UiTree` keep their sizes (§2.7). Builders `text_field(parent, value)`, `set_field_value`, `field_value`, `set_field_max`, `set_placeholder`. Layout then measures the value before the caret through a scratch node the field keeps in the store, and the caret, a 1-unit bar the line's height in the text's colour, sits at that width: on the glyph boundary for left-to-right text whose shaping joins nothing across the caret, off by a kerning pair or inside a ligature otherwise, and wrong for right-to-left text (Q-j); a caret move lays its root out once. No blink (Q-g).
- **Routing:** while a field holds focus, a text record inserts at the caret; Backspace, Delete, Left, Right, Home and End edit and move; Enter commits; Escape restores the value it had on focus and blurs; Tab and Shift+Tab, Up and Down move focus as today. Its keys never reach the game nor take `ui_accept` or `ui_left` meanings, a modal root or not. Events: `UiEvent::FieldChanged { widget, key }` at each edit, `UiEvent::FieldCommitted { widget, key }` on Enter.
- **Screen files:** kind `text_field` with `text` or `bind.text` (read at build), `placeholder`, `max` and `on`, which runs at commit; a game reads the value by the node's key.
- **Harness:** `UiHarness::type_text(&str)` and `Harness::type_text(&str)`, which record text as the bridge does.
