### 2.2 Settings: a game section, Bloom, the focus mute, the display (Step 1)

- **The game section (S-118):** `Settings` keeps the file's `game` value, an object the engine never reads: `Settings::game::<T: DeserializeOwned + Default>() -> T` (absent: `T::default()`; a value that does not deserialize: `T::default()` and a load warning, the file kept) and `set_game(&T)` for `T: Serialize`. It saves with the rest; an older build ignores it (unknown keys, A8).
- **Two engine switches:** `bloom: Option<bool>` and `mute_unfocused: Option<bool>`, with getters and setters, the file's `bloom` and `mute_unfocused`. Unset is on for Bloom and off for the mute.
- **The mute (S-145):** `tungsten::apply_settings` sends master volume 0 while `mute_unfocused` is on and the window has no focus. A focus change re-applies the master volume, inside the existing `display_input` system (no new system: each system is a timing entry a frame in every guard, A4). The game's `Settings` is never swapped.
- **Bloom and the tail (S-50):** a core resource `post::PostTail(pub Vec<PostPass>)`, drawn after `PostStack` and before a transition's pass. `compose_post_stack` takes the game's stack, the tail, the Bloom switch and the transition pass. It returns the game's stack itself when the tail is empty, Bloom is on and no transition runs, so a frame copies nothing new. Otherwise it fills the reused scratch, dropping `PostPass::Bloom` while the switch is off. `FrameDraw` gains `post: Vec<PostPass>`, the composed stack, filled only when the harness is not counting, so the guards allocate nothing new.
- **The display (S-120, S-147):** `engine_display_input_system` writes the toggled display mode or vsync into `Settings`, requests it through `apply_settings`' path and saves `Settings`; a failed save logs. `tungsten::requested_display(world) -> DisplayState` is the merge `apply_settings` makes of `Settings` over the live display, and `apply_settings` calls it.

### 2.3 The action map (Step 2)

- **Labels (S-68):** `input.json` takes an optional `labels` list, `[["move_up", "Move up"], …]`, in file order (Q12). Each action it names must be bound in the shipped map or the defaults; a `ui_` or `engine_` action fails the parse, so the menus cannot be lost (AGENTS.md's rule made the loader's). `ActionMap::labelled() -> &[(String, String)]` and `label(action)`; the user layer keeps the shipped labels and `persist` writes none.
- **Cells (S-124):** `Binding::is_gamepad()`; `BindingDevice { Keyboard, Gamepad }` (keyboard takes mouse bindings); `binding_at(action, device, index) -> Option<Binding>` and `set_binding_at(action, device, index, binding)`, which replaces that cell or appends.
- **Shipped and reset (S-168):** `shipped(action) -> &[Binding]`, the bindings under the user layer (`base`, else the map's own); `reset(action)` and `reset_all()` return to them. The caller persists, as with `replace_bindings`.

### 2.4 The harness, typed actions, the kit's hooks (Step 3)

- **Audio (S-44):** the harness logs every audio command of the frames it steps until `clear_audio_log()`, only when not counting. Queries over the log: `plays(sound_id)` (each play's voice, loop and fade, the ID resolved through `SoundRegistry`), `stops()` (voice and fade), `voice_volumes(voice)` (each change's level and fade) and `master_volumes()`. `audio()` stays the last frame's.
- **Taps (S-119):** `Harness::tap_action(action)` and `UiHarness::tap_key(key)`: down for a frame, up the next, two frames stepped.

### 2.5 Music per state (Step 4, S-63)

`GameState::music(&self) -> Option<StateMusic>`, default `None`; `StateMusic::new(sound_id, fade)`.

- **The rule:** the heard state is the top-most state on the stack that names music. Its voice plays at its sound's manifest level; every other music state's voice plays on at 0, keeping its place in the song. Each change fades over the incoming state's fade. A state's voice stops when it exits, faded over its own.
- **The mechanism:** the dispatcher applies the rule after a frame's commands change the stack, so a frame that changes nothing does nothing. The voices sit beside the stack's entries. A sound ID the registry lacks warns once and plays nothing.
- **What the rule gives:** Settings over the title keeps the title's song; pause over gameplay drops the run's song to 0 under pause's loop; a pop back brings it up; game over silences the run under its own music; a reset stops them all. A one-shot sting stays its state's (`on_enter`).
